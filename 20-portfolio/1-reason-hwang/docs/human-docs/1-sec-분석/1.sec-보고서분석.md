## 모델링 1 - 문서 구조          공시의 구성과 원문 위치 보존           Company, Filing, Item

- 원본을 Item 단위로 분할하고 제목·본문·출처 저장  

문서의 뼈대를 만드는 작업 
- PostgreSQL에 저장된 SEC 원본 HTML 가져와서 처리한다. 
- 회사를 식별 : CIK를 기준으로 Company를 찾거나 생
- 공시를 식별 : accession number를 기준으로 Filing을 생성 
- HTML에서 Item 경계 : 제목, 앵커, 문서 순서 등을 이용해 Item 1, 1A, 7, 8 등의 시작과 끝을 구분 
- Item과 원문 위치를 연결 하지 않는다.: 의존성 이슈, '원문에서 추출한 본문 텍스트를'를 저장  
- view를 위한 html구조는 유지한다. xml은 필요없다. (본문을 감싸는 XBRL 태그는 태그만 벗기고 안의 값)  

[스키마 리스트]
• 모델링 1은 노드 3종과 관계 2종을 기본  

-  Company ──FILED──▶ Filing ──HAS_ITEM──▶ Item

-   Company    제출 기업                  id, cik, name, ticker
-   Filing     공시 한 건                 id, accessionNo, formType, filingDate, reportDate, sourceUrl, sourceHash, parserVersion,
-   Item       공시의 Item별 가공 본문    id, partCode, itemCode, title, order, displayHtml, text, contentHash, sourceLocator

```
  • displayHtml: 제목·문단·목록·표 구조를 보존하고 XBRL 메타데이터·스크립트를 제거한 HTML.
  • text: 청킹·검색용 본문. 표 헤더·단위와 행·열의 의미를 보존한 텍스트.
  • sourceHash: PostgreSQL에서 가져온 원본의 해시.
  • contentHash: Item의 가공 결과 변경을 식별하는 해시.
  • sourceLocator: 원본의 Item 시작·종료 위치나 앵커 등 추적 정보.
  • parserVersion: 어떤 추출 규칙으로 만들어졌는지 식별하는 버전.
```

## 모델링 2 - 본문 검색·근거     Item을 나눈 청크, 임베딩, 원문 근거    Chunk, 선택적으로 Topic, Statement  

목적 : 저장된 Item 본문을 검색용 작은 청크로 분할하고 임베딩 생성  
-  1. 검색에 사용할 본문을 정리 - 모델링 1 활용  
-  2. Item 내부를 청크로 나눕니다. : 소제목과 문단 경계 구분, 표는 헤더·단위·관련 설명이 떨어지지 않도록 처리합니다.  
-  3. 각 청크의 출처를 기록합니다. :  filing_id, item_id, 청크 순서, 원문 위치, 내용 해시를 저장합니다. 앞뒤 청크 관계도 연결할 수 있습니다.
-  4. 임베딩을 생성합니다. : 청크 본문과 필요한 제목 문맥을 임베딩 모델에 전달하고, 결과를 Chunk.embedding에 저장합니다. 모델명·버전도 기록합니다.
-  5. Neo4j 벡터 인덱스로 검색합니다. : 질문 역시 같은 임베딩 모델로 변환해 관련 청크를 찾습니다. 이후 Item·공시·주변 문단 관계를 따라 근거를 확장합니다.

[스키마]
-'Source → Chunk → Topic → Statement → Fact → Entity' 모두 6개 지원
-   Source       입력 문서와 출처                  모델링 1의 Filing 또는 Item에 연결한 분석 입력
-   Chunk        분할된 본문                       Item 안의 문단·표·소제목 단위
-   Topic        본문에서 추출한 주제              경쟁, 물류, 규제 등
-   Statement    독립적으로 이해할 수 있는 진술    “회사는 배송망 확장에 투자하고 있다”
-   Fact         진술을 뒷받침하는 관계·사실       회사 — 투자한다 → 배송망
-   Entity       사실에 등장하는 개체              회사, 배송망, 규제기관 등

[모델링1과의 관계]
- Item 하나를 Lexical Graph의 Source 하나로 취급

## 모델링 3 - SEC 도메인 지식    재무 사실과 그 의미·맥락 표현          XbrlFact, Concept, Context, Dimension, Unit

목적 : 원본의 XBRL을 별도로 파싱해 재무 사실·기간·단위·차원 저장  

- 입력은 청킹된 텍스트가 아니라 원본 HTML의 Inline XBRL과 참조 taxonomy입니다. 이 경로는 모델링 2와 독립적으로 처리할 수 있습니다.
- 쿠팡 보고서의 실제 예를 사용하면:
```
  지표: RevenueFromContractWithCustomerExcludingAssessedTax
  contextRef: c-7
  unitRef: usd
  표시값: 26,312
  scale: 6
```
-  1. Concept를 읽습니다.:     name이 가리키는 재무 지표를 식별합니다. 접두사 문자열만 보지 않고 네임스페이스까지 보존해 회사별 확장 지표를 구분합니다.
-  2. Context를 읽습니다.    c-7을 찾아 기업·기간·차원을 해석합니다. 이 보고서에서는 쿠팡, 2025년, 상품 분류입니다.
-  3. Dimension과 분류값을 읽습니다.     ProductOrServiceAxis → ProductMember를 연결합니다. 따라서 모델에는 Dimension뿐 아니라 Member 또는 차원값을 표현하는 구조도 필요합니다.
-  4. Unit과 수치를 해석합니다.     단위, 표시 형식, 배율, 부호 등을 적용합니다. 예시의 26,312 × 10⁶은 26,312,000,000 USD입니다. 원래 표시값과 정규화한 값을 함께
     보존합니다.
-  5. 재무 사실과 출처를 저장합니다. : 정밀도를 보존할 수 있는 방식으로 값을 저장하고, 공시·원문 태그 ID·파서 버전을 기록합니다.

  XbrlFact
  ├─ Concept: 매출
  ├─ Context
  │  ├─ 기업: 쿠팡
  │  ├─ 기간: 2025-01-01 ~ 2025-12-31
  │  └─ 상품·서비스 분류: 상품
  ├─ Unit: USD
  ├─ Value: 26,312,000,000
  └─ 원문 출처: 해당 공시의 f-57

-  이 단계에서는 중복 출현과 값 충돌을 구별해야 합니다. 같은 사실이 본문과 주석에 반복되면 출처를 여러 개 연결할 수 있지만, 값이 다르면 무조건 합치지 않습니다.
-  또한 다른 회사가 정의한 비슷한 지표를 이름만 보고 같은 지표로 합치지 않습니다. 회사 간 비교를 위한 지표 매핑은 별도로 검증해야 합니다.

```

                              │                                                ├─ OF_DIMENSION →
                              Dimension
                              │                                                └─ HAS_MEMBER → Member
                              └─ IN_UNIT ─────▶ Unit

```
   XbrlFact          보고된 재무 값 한 건                id, valueType, rawValue, normalizedValue,
                                                         decimals, scale, isNil, parserVersion
-   Concept           무엇을 측정한 값인지                id, namespaceUri, localName, label,
                                                         dataType, periodType, balance
-   Context           기업·기간·차원의 조합               id, sourceContextIds, periodType,
                                                         startDate, endDate, instantDate
-   Dimension         분류 기준                           id, namespaceUri, localName, label, kind
-   Member            미리 정의된 분류값                  id, namespaceUri, localName, label
-   DimensionValue    특정 기준에 어떤 값이 지정됐는지    id, kind, typedValue
-   Unit              수치의 단위                         id, canonicalExpression

[분류 체계]

중요도와 별도로 Fact가 무엇에 관한 정보인지 분류한다. 아래 경계 규칙을 적용해 Fact당 하나의 분류만 부여하고, 기타로 나머지를 포괄하는 MECE 방식으로 운영한다.

1. **사업 KPI와 운영 성과** — `OPERATING_PERFORMANCE`: 고객·가입자·거래액·판매량, 제품·사업부·지역별 실적, 수익성·운영 효율. KPI를 이 분류에 포함한다.
2. **투자와 사업 재편** — `INVESTMENT_AND_RESTRUCTURING`: 설비 투자, 전략적 지분 투자, 인수·매각, 사업 진출·철수.
3. **거래 의존과 계약 의무** — `DEPENDENCIES_AND_COMMITMENTS`: 고객·공급업체·지역 집중도, 구매 약정, 리스, 공급자 금융.
4. **자본 구조와 주주 권리** — `CAPITAL_AND_SHAREHOLDER_RIGHTS`: 차입·주식 발행, 배당·자사주 매입, 의결권·주식 희석.
5. **법률·규제와 사고** — `LEGAL_REGULATORY_AND_INCIDENTS`: 소송, 규제 조치, 세무 분쟁, 사이버 사고·보상.
6. **기타** — `OTHER`: 위 다섯 범주에 해당하지 않는 사실. 중요도 선별을 통과한 경우에만 게시하며, 근거 부족을 기타로 대체하지 않는다.

[분류 경계 규칙]

- 중요해 보이는 영향이 아니라 Fact가 직접 측정하는 대상을 기준으로 분류한다.
- 인수 대금은 투자와 사업 재편, 인수 재원으로 조달한 차입금은 자본 구조와 주주 권리로 분류한다.
- 신규 사업부 매출은 사업 KPI와 운영 성과, 해당 사업의 투자액은 투자와 사업 재편으로 분류한다.
- 고객 수·고객당 매출은 사업 KPI와 운영 성과, 특정 고객의 매출 비중은 거래 의존과 계약 의무로 분류한다.
- 리스·구매 약정·공급자 금융은 거래 의존과 계약 의무, 일반 차입은 자본 구조와 주주 권리로 분류한다.
- 소송·규제·사고에서 직접 발생한 보상액·벌금은 지급 의무여도 법률·규제와 사고로 분류한다.
- 자사주 매입 승인액은 자본 구조와 주주 권리로 분류하며, 미래 지급 의무로 해석하지 않는다.

{text}

`{topics}`에는 다음 공통 목록을 전달한다.

```text

```

Assign every statement to the closest selected topic without changing the statement. Do not invent more specific topics or a topic for each consequence or metric.
ENTITIES: named companies, business segments, products/services/programs, regulators and locations are eligible. Additionally allow a concrete input/resource or clearly described risk mechanism ONLY when it is a material dependency or exposure in an explicit relationship. Use short stable names and merge synonyms. Do not promote every noun into an entity. Generic customers, suppliers, competitors, users, generic products/services, channels, metrics, ordinary descriptions, every item of a list, and secondary consequences should stay in statement text. For example, memory components may be a material dependency, while rising costs should normally remain a qualification. Risk mechanisms may be entities when indispensable to a meaningful risk link, not simply because a sentence describes a risk. No artificial node minimum or count target. Entity classes: Company, Business Segment, Product, Service, Program, Regulator, Location, Resource, Risk Factor.
FACTS: select the primary meaningful business/dependency/risk links, rather than all possible triples. Keep causal context in statements. Named-entity relationships and concrete dependencies are both permitted. Usually one or two primary links suffice; do not force a link when none is useful. Do not add entity-classification facts, duplicate inverse relations, or every member of an enumeration. Preserve modality (MAY_*, EXPECTS_*, etc.) and negation when extracting a conditional or negative link. actual entity|allowed class
proposition: EXACT supplied statement on the SAME LINE
entity-entity relationships:
actual entity|RELATION|actual entity
entity-attributes:
actual entity|ATTRIBUTE|concise value
Repeat proposition blocks, and topic blocks only when needed. Omit empty relationship/attribute sections. For EVERY fact-free statement, repeat the exact statement on one plain detail line immediately below its proposition line, so the Toolkit parser preserves it. Never emit an empty proposition value.
Statements:
{text}
```

- **GET** `/internal/sec-modeling/filings/{cik}/{accession}/results/{stage}`: 단계별 결과 (`offset`, `limit`)
- **POST** `/api/sec-analysis/search`: Chunk·Statement 검색 (`query`, `filingIds`, `itemCodes?`, `topK?`)
- **POST** `/api/sec-analysis/facts/query`: 선별 XBRL 조회 (`filingIds`, `analysisCategory?`, 기간·차원·단위 등)
- **GET** `/api/sec-analysis/evidence/{evidenceId}`: 가공 본문·원문 근거 조회
- **POST** `/internal/sec-modeling/model-{stage}/runs`: 실행 (`runId`, `executionToken`, 공시·입력 정보); NDJSON 응답
- **GET** `/internal/sec-modeling/runs/{runId}`: 실행 상태 조회
- **POST** `/internal/sec-modeling/runs/{runId}/cancel`: 실행 취소 (`executionToken`)

- 기존 Agent 도구: `search_sec_evidence`, `query_sec_xbrl_facts`, `get_sec_evidence`.
- 실행·재시도 관리는 BFF 경유. 현재 `/openapi.json`에는 SEC 명세가 누락되어 있음.
