# Open DART 공시 API 전체 기능 카탈로그

> 공식 개발가이드 확인일: **2026-11-14**. 금융감독원 Open DART의 6개 API 그룹, **논리 API 85개**를 정리한다. JSON/XML 표현 형식을 각각 별도 기능으로 세지 않는다. 이 문서는 외부 API 조사 문서이며, 현재 프로젝트에 모든 API가 구현되어 있다는 의미가 아니다.
>
> 인증이 필요 없는 공식 개발가이드만 열람했다. **실제 인증키를 사용하거나 API 데이터를 조회하지 않았다.** 아래 요청은 실행 예시이고, 응답의 `<…>` 값은 구조 설명용 자리표시자다. 실제 회사의 조회 결과·실제 재무 수치로 해석하지 않는다.

## 2. 공통 호출 규칙

### 2.1 기본 주소·인증·식별자

- 기본 주소는 `https://opendart.fss.or.kr/api/`, 메서드는 아래 85개 모두 **GET**, 문자 인코딩은 UTF-8이다.
- 모든 요청에 `crtfc_key`가 필요하다. 공식 요청 타입은 `STRING(40)`이다. 키는 서버 환경변수·비밀 저장소에서 주입하고 브라우저 코드, Git, 공유 URL·로그에 넣지 않는다.
- 대부분 `.json`과 `.xml`을 제공한다. 단, **`document.xml`, `corpCode.xml`, `fnlttXbrl.xml`의 성공 응답은 ZIP 바이너리**다. 확장자만 보고 XML 파서를 적용하면 안 된다.

| 식별자 | 의미 | 처리 원칙 |
| --- | --- | --- |
| `corp_code` | DART 고유번호, 8자리 | 문자열로 보존. `corpCode.xml`의 회사명·종목코드와 매핑한다. |
| `stock_code` | 상장 종목코드, 6자리 | DART 고유번호와 다르다. 비상장 회사는 비어 있을 수 있다. |
| `rcept_no` | 공시 접수번호, 14자리 | 공시검색 결과의 값을 사용한다. 원문 다운로드·DART 뷰어 연결에 사용한다. |
| `bsns_year` | 사업연도, 4자리 | 공시 접수연도와 항상 같지 않다. |
| `reprt_code` | 정기보고서 종류 | 아래 코드표를 사용한다. |

미국 SEC의 CIK·accession number와 DART의 고유번호·접수번호는 서로 다른 식별체계다. 숫자 모양이 비슷해도 변환하거나 재사용하지 않는다.

### 2.2 보고서·재무 구분 코드

| 키 | 값 | 의미 |
| --- | --- | --- |
| `reprt_code` | `11013` | 1분기보고서 |
| `reprt_code` | `11012` | 반기보고서 |
| `reprt_code` | `11014` | 3분기보고서 |
| `reprt_code` | `11011` | 사업보고서 |
| `fs_div` | `CFS` / `OFS` | 연결재무제표 / 별도재무제표 |
| `corp_cls` | `Y` / `K` / `N` / `E` | 유가증권 / 코스닥 / 코넥스 / 기타 |
| `idx_cl_code` | `M210000` | 수익성지표 |
| `idx_cl_code` | `M220000` | 안정성지표 |
| `idx_cl_code` | `M230000` | 성장성지표 |
| `idx_cl_code` | `M240000` | 활동성지표 |

재무 응답의 `sj_div`에서 `BS`는 재무상태표, `IS`는 손익계산서, `CIS`는 포괄손익계산서, `CF`는 현금흐름표, `SCE`는 자본변동표다. **택사노미 API 요청의 `sj_div`는 `BS1`, `IS1`, `CF1` 같은 별도 상세 코드**를 사용하므로 서로 그대로 대입하지 않는다.

### 2.3 자주 쓰는 요청 묶음

각 API 상세에는 실제 필수·선택 키를 다시 명시한다. 다음 묶음은 읽기 편의를 위한 분류다.

| 요청 묶음 | 필수 키 (`crtfc_key` 공통) | 비고 |
| --- | --- | --- |
| 회사 지정 | `corp_code` | 기업개황·지분공시 API |
| 정기보고서 | `corp_code`, `bsns_year`, `reprt_code` | DS002 대부분 및 재무 주요계정 |
| 전체 재무제표 | 정기보고서 키 + `fs_div` | `fnlttSinglAcntAll` |
| 재무지표 | 정기보고서 키 + `idx_cl_code` | 단일·다중회사 지표 |
| 기간별 주요 공시 | `corp_code`, `bgn_de`, `end_de` | DS005·DS006. 날짜는 `YYYYMMDD`. |
| 공시 원문 | `rcept_no` | `document.xml` |
| XBRL 원문 | `rcept_no`, `reprt_code` | `fnlttXbrl.xml` |
| 택사노미 | `sj_div` | 해당 상세 가이드의 코드표 확인 |
| 고유번호 전체 파일 | 추가 키 없음 | 인증키만 지정 |

다중회사 API의 `corp_code`는 쉼표로 연결한 회사 코드 목록이다. 단일회사 API에 임의로 여러 코드를 전달하지 않는다. `fnlttMultiAcnt`는 최대 100개 회사, 주요 재무지표 다중회사 API도 공식 상세의 요청 가능 회사 수를 확인하고 배치한다.

### 2.4 응답과 오류

HTTP 성공 여부와 **본문 `status`**를 별도로 검사한다. 일반 JSON API의 대표 구조는 다음과 같다. 이 예시는 실제 데이터가 아니다.

```json
{
  "status": "000",
  "message": "정상",
  "list": [
    { "rcept_no": "<접수번호>", "corp_code": "<고유번호>", "corp_name": "<회사명>" }
  ]
}
```

`company.json`은 기업개황 필드가 최상위에 위치한다. `list.json`에는 `page_no`, `page_count`, `total_count`, `total_page`가 추가된다. DS006은 `group[].title`과 `group[].list[]`를 갖는다. 보수 V2는 인적·사업연도 그룹 아래 세부 보상 목록이 있으므로 **모든 API를 `list[]` 한 형태로 처리하면 안 된다.** XML 표의 `result`는 루트·구조 표기일 수 있으며 JSON에 동일한 `result` 래퍼가 있다고 단정하지 않는다.

| 본문 상태 | 의미·대응 |
| --- | --- |
| `000` | 정상. 해당 API의 실제 응답 구조를 파싱한다. |
| `010`, `011`, `012` | 미등록 키·사용 불가 키·접근 IP 문제. 인증·등록 설정을 확인한다. |
| `013` | 조회 결과 없음. 빈 데이터와 인증 실패를 구분한다. |
| `014` | 파일이 존재하지 않음. 원문·XBRL 파일 가용성을 확인한다. |
| `020` | 요청 제한 초과. 호출을 줄이고 키별 제한을 확인한다. 일반 안내의 20,000건 기준을 모든 키의 보장 한도로 해석하지 않는다. |
| `021` | 조회 가능한 회사 수 초과. 다중회사 요청을 나눈다. |
| `100`, `101` | 필드 오류·부적절한 접근. 요청 키와 값 형식을 확인한다. |
| `800`, `900` | 점검·정의되지 않은 오류. 공식 상태를 확인하고 제한적으로 재시도한다. |
| `901` | 개인정보 보유기간 만료로 사용 불가한 키. 키 관리 절차를 확인한다. |

상태 코드는 각 API의 공식 상세 페이지 하단 메시지 설명을 기준으로 한다. 네트워크 오류와 `013`을 같은 실패로 합치거나, 빈 금액 문자열을 임의로 0으로 바꾸지 않는다.

### 2.5 안전한 호출 예시 함수

아래는 **실행하지 않은 Bash 예제**다. 실제 인증키를 문서에 넣지 않는다. `CORP_CODE`, `RCEPT_NO` 등은 앞 단계에서 얻은 값을 환경변수로 지정한다. 예시의 사업연도·조회 기간은 원하는 범위로 바꾼다.

```bash
# DART_API_KEY는 안전한 실행 환경에서 별도로 주입한다.
# CORP_CODE='<DART 고유번호 8자리>'
# CORP_CODES='<고유번호1>,<고유번호2>'
# RCEPT_NO='<실제 공시검색 결과의 접수번호 14자리>'

dart_json() {
  local endpoint="$1"
  shift
  local -a args=(--data-urlencode "crtfc_key=${DART_API_KEY:?인증키 환경변수 필요}")
  local argument
  for argument in "$@"; do args+=(--data-urlencode "$argument"); done
  curl --silent --show-error --fail-with-body --get \
    "https://opendart.fss.or.kr/api/${endpoint}" "${args[@]}"
}
```

이 함수는 본문의 `status`를 판정하지 않는다. JSON 결과를 받은 호출자가 반드시 확인해야 한다. XML 표현이 필요한 일반 API는 경로의 `.json`을 `.xml`로 바꾼다. ZIP 세 종류는 아래 전용 다운로드 절차를 따른다.

## 3. DS001 — 공시정보 (4개)

먼저 고유번호 파일로 회사 식별자를 확보하고, 공시검색으로 접수번호를 찾은 다음 공시 원문을 받는 흐름이다.

공시검색의 주요 선택 조건:

| 키 | 기본값·범위 |
| --- | --- |
| `corp_code` | 생략 가능. 생략 시 검색 기간은 3개월 이내로 제한된다. |
| `bgn_de`, `end_de` | 접수일 기준 `YYYYMMDD`. 시작일 기본은 종료일, 종료일 생략 시 당일 기준이다. |
| `last_reprt_at` | `N` 기본: 정정을 포함한 제출 보고서 전체. `Y`: 최종보고서만 검색. |
| `pblntf_ty` | `A` 정기공시, `B` 주요사항, `C` 발행, `D` 지분, `E` 기타, `F` 외부감사, `G` 펀드, `H` 자산유동화, `I` 거래소, `J` 공정위 |
| `pblntf_detail_ty` | 공식 세부 유형 코드. 예: `A001` 사업보고서. 세부 코드 전체는 상세 가이드 참조. |
| `corp_cls` | `Y/K/N/E` 중 하나. 생략 시 전체, 복수 조건은 지원하지 않는다. |
| `sort`, `sort_mth` | `date`·`crp`·`rpt`, `asc`·`desc`. 기본 `date`, `desc`. |
| `page_no`, `page_count` | 기본 1페이지·10건, 페이지당 최대 100건 |

검색 응답의 `report_nm`, `rm` 및 원문을 함께 확인해 정정·철회·첨부 정정 여부를 판단한다. `last_reprt_at=Y`는 서로 다른 공시를 법률적으로 병합해 준다는 뜻이 아니다. 접수번호로 연결하는 공식 뷰어 형태는 `https://dart.fss.or.kr/dsaf001/main.do?rcpNo=<접수번호>`다.

### DS001-01 공시검색

- **엔드포인트:** `GET /api/list.json` / `GET /api/list.xml`
- **요청:** `crtfc_key` 필수, `corp_code` 선택, `bgn_de` 선택, `end_de` 선택, `last_reprt_at` 선택, `pblntf_ty` 선택, `pblntf_detail_ty` 선택, `corp_cls` 선택, `sort` 선택, `sort_mth` 선택, `page_no` 선택, `page_count` 선택
- **대표 응답 필드:** `page_no` 페이지 번호; `page_count` 페이지 별 건수; `total_count` 총 건수; `total_page` 총 페이지 수; `corp_cls` 법인구분; `corp_name` 종목명(법인명); `corp_code` 고유번호; `stock_code` 종목코드; `report_nm` 보고서명; `rcept_no` 접수번호; `flr_nm` 공시 제출인명; `rcept_dt` 접수일자
- **전체 요청·응답 명세:** [공시검색 공식 개발가이드](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001)

```bash
dart_json list.json "corp_code=$CORP_CODE" bgn_de=20250101 end_de=20251231 page_no=1 page_count=100
```

### DS001-02 기업개황

- **엔드포인트:** `GET /api/company.json` / `GET /api/company.xml`
- **요청:** `crtfc_key` 필수, `corp_code` 필수
- **대표 응답 필드:** `corp_name` 정식명칭; `corp_name_eng` 영문명칭; `stock_name` 종목명(상장사) 또는 약식명칭(기타법인); `stock_code` 상장회사인 경우 주식의 종목코드; `ceo_nm` 대표자명; `corp_cls` 법인구분; `jurir_no` 법인등록번호; `bizr_no` 사업자등록번호; `adres` 주소; `hm_url` 홈페이지; `ir_url` IR홈페이지; `phn_no` 전화번호
- **전체 요청·응답 명세:** [기업개황 공식 개발가이드](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019002)

```bash
dart_json company.json "corp_code=$CORP_CODE"
```

### DS001-04 고유번호

공통 요청은 인증키 + 회사 고유번호 + 사업연도 + 보고서 코드다. 응답의 `rcept_no`, `corp_cls`, `corp_code`, `corp_name`, `stlm_dt`와 아래 항목별 필드를 함께 저장한다. 공식 가이드별 제공 시작 시점·보고서 가용성을 따르며, 모든 회사·모든 분기에 모든 표가 있다고 가정하지 않는다.

## 5. DS003 — 정기보고서 재무정보 (7개)

## 9. 원문·고유번호·XBRL 다운로드 예시

### 9.1 ZIP 세 종류의 차이

| 엔드포인트 | 요청 | 성공 시 내용 | 목적 |
| --- | --- | --- | --- |
| `corpCode.xml` | 인증키 | 회사 식별 정보 XML을 포함한 ZIP | 전체 회사 코드·이름·종목코드 매핑 |
| `document.xml` | 인증키 + `rcept_no` | 해당 접수 공시 원문 파일을 담은 ZIP | 공시 본문·표·원문 근거 확보 |
| `fnlttXbrl.xml` | 인증키 + `rcept_no` + `reprt_code` | XBRL 재무제표 관련 파일 ZIP | XBRL 인스턴스·관련 원본 분석 |

이름이 `.xml`로 내려받아지더라도 실제 ZIP일 수 있다는 공식 주의사항이 있다. 저장 파일명을 `.zip`으로 지정하더라도 **내용이 정말 ZIP인지 검사**해야 한다. HTTP 200 오류 XML을 ZIP으로 오인하지 않는다.

```bash
curl --silent --show-error --fail-with-body --get \
  'https://opendart.fss.or.kr/api/corpCode.xml' \
  --data-urlencode "crtfc_key=$DART_API_KEY" \
  --output corp-codes.zip

curl --silent --show-error --fail-with-body --get \
  'https://opendart.fss.or.kr/api/document.xml' \
  --data-urlencode "crtfc_key=$DART_API_KEY" \
  --data-urlencode "rcept_no=$RCEPT_NO" \
  --output disclosure.zip

curl --silent --show-error --fail-with-body --get \
  'https://opendart.fss.or.kr/api/fnlttXbrl.xml' \
  --data-urlencode "crtfc_key=$DART_API_KEY" \
  --data-urlencode "rcept_no=$RCEPT_NO" \
  --data-urlencode 'reprt_code=11011' \
  --output financial-xbrl.zip

# ZIP 검사를 통과한 파일만 후속 처리한다.
unzip -t corp-codes.zip
unzip -l disclosure.zip
unzip -l financial-xbrl.zip
```

ZIP 파일명·내부 파일 구성을 고정 문자열 하나로 가정하지 말고 목록을 검사한다. 서버에서 압축을 풀 때는 경로 탈출, 과도한 압축 해제 크기, XML 외부 엔티티를 차단한다. 원문 HTML/XML은 실행 가능한 페이지로 신뢰하지 않고 파싱·격리 미리보기 대상으로 취급한다.

`corpCode.xml` 내부 회사 항목의 구조 예시는 다음과 같다. 값은 모두 자리표시자다.

```xml
<result>
  <list>
    <corp_code>고유번호_8자리</corp_code>
    <corp_name>회사명</corp_name>
    <corp_eng_name>영문_회사명</corp_eng_name>
    <stock_code>종목코드_또는_공란</stock_code>
    <modify_date>YYYYMMDD</modify_date>
  </list>
</result>
```

## 10. 실무 적용 순서

1. **회사 기준정보**: 고유번호 ZIP을 받아 DART 코드·종목코드 매핑을 만들고 변경일을 기록한다. 종목코드가 없는 회사도 임의 삭제하지 않는다.
2. **공시 색인**: 공시검색을 회사·접수 기간별로 페이지 순회한다. 접수번호를 원문·정정 추적의 기준으로 보존한다.
3. **구조화 항목**: 보고서 종류·사업연도에 맞는 DS002/DS003을 사용하고, 사건별로 DS004/DS005/DS006을 보완한다.
4. **근거 원문**: 원문 ZIP과 필요한 XBRL을 내려받아 파일 형식·무결성·출처를 검증한다. 구조화된 일부 항목만으로 원문 전체를 읽었다고 간주하지 않는다.
5. **정정·시점 관리**: 같은 사업연도에도 접수번호와 정정에 따라 값이 달라질 수 있다. 조회 시각, 원문 접수번호, 연결/별도, 기간, 통화를 함께 저장한다.
6. **운영**: 키별 제한·오류 코드에 맞게 호출을 제한하고 필요한 결과를 캐시한다. 실패를 무제한 재시도하거나 조회 없음과 오류를 섞지 않는다.

이 카탈로그는 공개 개발가이드에 명시된 기능과 계약을 정리한 것이다. 실제 키의 권한·호출 한도, 특정 회사·접수 건의 데이터 가용성, 요청 성공 여부는 인증 호출을 통해 별도로 검증해야 한다. 금융감독원도 구조화 정보의 정확성·완전성을 보장하지 않으므로 중요한 분석은 해당 보고서 원문과 대조한다.
