# 직무 문제 해결 미션 편집 검토

- 날짜: 2026-09-21
- 범위: 신규 디자인 20개 자체 검토 및 IT 운영 20개 동료 검토
- 상태: 디자인 자체 검토 및 IT 20개 독립 동료 검토 완료. 디자인 독립 동료 검토는 별도 문서에 기록한다.
- 판정 경계: 원문 내용과 구조를 검토한 로컬 초안이다. 실제 AI 대화·기술 조치·학습 효과를 검증한 결과가 아니다.

## 디자인 20개 작성자 자체 검토

대상은 `assets/missions/authoring/work-designer.json`이다. A2/B1/B2/C1/C2 각 4개, 전부 4단계로 구성했다. 20개 모두 실제 문제가 제시되고, 상대에게 모르는 정보를 확인한 뒤 대안을 제안하며 담당·시간·후속 행동을 정한다.

| 수준 | 독립 문제 과업 |
|---|---|
| A2 | 모바일 오류 상태 누락, 흐린 이미지와 내보내기 용도, 빈 버튼 문구와 실제 동작, 최신 디자인 파일의 편집 권한 |
| B1 | 색에만 의존한 상태 표시, 삭제 확인창 혼동, 긴 번역 문구 넘침, 연구 참가자 결석과 보고 범위 |
| B2 | 브랜드와 가격 식별, 핸드오프 상태의 우선순위, 숙련 표본의 신규 사용자 일반화, 공통 컴포넌트의 기능 불일치 |
| C1 | 키보드 진행 불가와 승인 권한, 가입 증가와 취소 문의 증가, 고객의 마무리 요청에 숨은 신규 범위, 긍정 발언과 과업 실패의 다른 의미 |
| C2 | 실수 방지와 해지 방해의 구분, 불확실한 연구의 투자 의미, 임원 해법과 실제 사용자 문제, 연구 녹화의 사용 목적 변경 |

자체 점검에서 `designer-scope-hidden-in-polish`의 예문이 수요일 회의를 tomorrow라고 표현하는데 상황의 현재 요일이 없어, 오늘은 화요일이라는 가상 사실을 명시했다.

구조 확인은 Python으로 수행했다. 20개, 수준별 4개, 고유 designer- slug, 3~5 범위 내 4개 단계, 모든 caseBrief의 배열·권한·상대 입장·상위 검토 경로가 존재함을 확인했다. scenario와 caseBrief.situation, outcome과 caseBrief.deliverable의 일치를 검사했다.

디자이너가 법적 적합성·전체 접근성·정책·투자를 단독 승인하는 것으로 설정하지 않았다. 기술적 규범을 암기하는 대신 실제 관찰·제약·권한을 확인하는 언어 과업이다. 가상 성능 수치나 참가자 수는 해당 시나리오의 입력이며 외부 연구 결과가 아니다. 사례의 우수성을 검증하는 실제 사용자 연구는 아직 수행하지 않았다.

## IT 운영 독립 동료 검토

대상은 `assets/missions/authoring/work-it-operations.json`이다. 작성자가 최종 저장을 확인한 뒤 수정 소유권을 넘겨받았다. 20개의 원문을 전부 읽었다. 상황·상대역·첫 발화·단계 예문·cue·전이·caseBrief 전체를 읽었으며 출력에서 일부 잘린 14~15번은 별도로 재열람했다.

영어 자연스러움, 수준 부담, 정보와 예문의 일치, 학습자의 권한, 시간 계산, 실제로 책임이 이어지는지 확인했다. 특히 계획을 말하는 것과 실제 담당자가 수락한 것을 구분했다.

| slug | 발견과 수정 |
|---|---|
| it-ticket-missing-details | A2 첫 질문이 도구와 표시를 한 번에 물어, 한 가지씩 질문한다는 완료 기준과 불일치했다. 두 질문을 별도 단계로 나눠 총 5단계로 했다. |
| it-handover-unfinished-recovery | 18:10 결과를 받는 담당자에게 after six에 연락하라고 해 결과 이전 연락으로도 해석될 수 있었다. 18:10 결과를 받은 다음 고객에게 연락하도록 순서를 명시했다. |
| it-vendor-status-without-eta | 13:40 벤더 결과 후 10분짜리 백업 링크를 만들면 13:45 공지 기한을 지킬 수 없었다. 현재 13:30에 내부 진행자에게 병행 준비를 요청하고 13:40 상태로 전환을 판단하도록 수정했다. deliverable·입력·완료 기준을 함께 맞췄다. |
| it-partial-recovery-customer-note | 기술 재확인과 고객 공지가 모두 15:30이라 완료 결과가 나와야만 공지 가능한 것으로 오해할 수 있었다. 검사가 진행 중이어도 현재 상태를 15:30에 안내하도록 했다. |
| it-suspicious-login-report | 본인이 통제하지 못하는 보안팀 접수를 15분 내 확정하겠다고 약속했다. 15분 내 접수 여부와 다음 연락·상위 보고 단계를 안내하겠다는 약속으로 바꿨다. |
| it-time-zone-ownership-gap | 한국 팀 리드의 09:40 연락 종료와 북미 팀의 10:00 수락 사이 20분 공백이 남았다. 글로벌 당직자 Jo의 09:40 이후 연락 책임과 10:00 수락 확인을 명시적으로 확보하는 단계를 추가했다. 수락 미확보 시 현재 리드가 종료 전 공식 교대 책임자에게 알려야 함을 명시했다. |
| it-incident-label-versus-exposure | 보안 분류 자체를 30분 안에 완료하라는 요청은 상대의 가용성을 알기 전 확약처럼 들릴 수 있었다. 즉시 전달하고 분류가 미완료여도 30분 안에 상태와 연락 담당을 확인하는 계획으로 바꿨다. |

수정 후 Python 파싱·집계로 20개, A2~C2 각 4개, 모든 단계 수 3~5개, outcome과 caseBrief.deliverable 일치를 확인했다. 도구 실행을 위한 명령을 추가하지 않았고, 임의로 실제 운영 조치·계정 권한 변경·보안 사고 확정·외부 신고 판단을 내리는 과업으로 바꾸지 않았다.

## 남은 검증

- 수정 원본을 부모 작업의 compiler로 재생성하고 전체 schema·참조 검증을 수행해야 한다.
- 이 검토는 영어 교재 초안과 가상 협의 계획에 대한 동료 편집이다. 실제 운영 상황에서 이 계획이 보편적으로 충분하다는 증거가 아니다.
- 상대 역할의 정보 제공과 협의가 실제 AI 실행에서도 유지되는지, 학습자가 예문 없이 해결안을 만들 수 있는지, 직무별 현실 필요성이 높은지는 별도 실행·학습자 검증이 필요하다.
