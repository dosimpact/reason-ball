# LEARN-05 다섯 평가 축과 턴 평가 설계 감사

작성일: 2026-09-11

## 범위와 증거 한계

부모가 확인한 Tier Verify graph 프로젝트는 todo/proxy뿐이며 대상 web 프로젝트는 notindexed다. web generation은 없다. 부모의 `check_index_coverage`에서 `src/entities/mission-run`, `src/app/api/ai/evaluate`, `src/features/mission-evaluation`, `tests/e2e/live/evaluation-axes.spec.ts`가 notindexed여서 해당 실제 소스를 직접 읽었다. 추가로 운영 hydration, 메시지 도움말, 학습 도움 API를 읽었다. 이 문서는 읽기 전용 코드 감사다. 브라우저·실제 AI·원격 DB 검증을 실행하지 않았으며 기존 테스트의 주석이나 assertion을 실제 실행 결과로 간주하지 않는다.

권위 있는 요구사항은 `docs/01-business/character-english-chat.business.md`의 8.4 LEARN-05와 11.2 전체다. LEARN-05 표는 턴별 의미 전달·문법·어휘·자연스러움과 근거를 요구한다. 11.2는 과업 달성·이해 가능성·문법·어휘 및 표현·상호작용이라는 다섯 축과 모든 점수의 관찰 가능한 근거를 요구한다. 평가가 공인 시험 점수처럼 표시되어서는 안 된다.

## 충실한 구현 경계

### 새로운 평가 다섯 축

새 평가에는 과업 달성, 이해 가능성, 문법, 어휘·표현의 자연스러움, 상호작용을 독립된 키와 설명으로 표현한다. 예를 들어 새 이해 가능성은 `comprehensibility`, 상호작용은 `interaction`으로 구분하고 과거 `appropriateness`를 legacy로 유지할 수 있다. 이름 변경만으로 기존 상황 적절성 점수가 이해 가능성 점수가 되지는 않는다.

- 과업 달성: 현재 발화 또는 전체 대화의 의도가 실제 목표에 기여했는지와 남은 목표를 설명한다.
- 이해 가능성: 상대가 무엇을 이해할 수 있었는지, 추가 추론이 필요한 부분은 무엇인지 설명한다.
- 문법: 학습 수준에 중요한 원문 오류와 짧은 수정에 연결한다. 올바른 원문에 가짜 오류를 만들지 않는다.
- 어휘·표현: 목표 단어 출현 횟수만 보지 않고 상황에 자연스러운 대안에 연결한다.
- 상호작용: 앞 질문에 실제로 답했는지와 대화를 이어 가는 다음 전략을 설명한다. assistant 질문은 문맥일 뿐 학습자의 성공 근거가 아니다.

새 점수의 가중치와 통과 규칙은 명시적 제품 정책으로 정하고 계약 테스트로 고정해야 한다. 기존 계산은 taskCompletion 40%, 나머지 세 축 각각 20%다. 다섯 축으로 바꾸면서 이 네 축 계산을 그대로 두거나 새 축을 과거 총점에 소급 적용하지 않는다. 저장된 total_score, passed, 보상, 최고 기록은 다시 계산하지 않는다. 새 rubric version을 저장하면 이전과 새 기준을 UI에서 구분할 수 있다.

### 선택한 턴과 전체 미션의 분리

LEARN-05의 `턴 평가`를 충족하려면 특정 완료된 사용자 메시지에서 명시적으로 평가를 요청하고 그 메시지의 의미·문법·어휘·자연스러움 및 상호작용을 확인할 수 있어야 한다. 모든 메시지마다 자동 AI 요청을 보내야 한다는 요구는 문서에 없다. 사용자 요청 방식은 summary 교정 모드와도 양립한다.

서버는 소유 대화와 선택 메시지 ID를 검증하고 실제 저장된 선택 턴 및 그 이전 관련 대화만 문맥으로 사용해야 한다. 이후 사용자가 정정한 문장이나 assistant가 답을 알려 준 내용을 앞선 턴의 능력으로 소급 평가하지 않는다. assistant 메시지·타 계정 메시지·진행 중인 사용자 메시지는 선택 대상에서 거부한다. 선택 턴의 평가 근거는 해당 사용자 ID를 가리켜야 한다.

턴 평가가 전체 미션 완료 API를 재사용해 미션 상태, 단계 완료, 점수, XP, 보상을 바꾸면 안 된다. 현재 `/api/ai/evaluate`는 평가 INSERT 후 단계 진행과 실행 상태를 갱신하고 UI는 보상 완료를 시도하므로 여기에 선택 턴을 단순 전달하는 방식은 부적합하다. 턴 학습 피드백을 별도 scope로 분리하고 UI에도 전체 미션 평가와 구별되는 이름을 쓴다. 필요한 저장 방식은 현재 DB 모델을 추가 확인한 뒤 정한다. 이 감사에서는 새 테이블 필요 여부를 판정하지 않았다.

LEARN-02는 진행 중/완료 목표와 현재 단계 표시 문제다. 턴 평가로 그 단계가 자동 완료됐다고 주장하지 않는다. 반대로 자동 목표 추적을 먼저 구현해야만 LEARN-05를 구현할 수 있는 것도 아니다. 두 기능을 연결한다면 서버 완료 조건과 발화별 평가 경계를 각각 검증해야 한다.

### 근거와 오류 처리

생성 결과 schema의 `evidence.min(1)`만으로 충분하지 않다. 현재 코드는 이후 `messagesById`에 없는 ID를 제거하므로 최종 evidence가 비어도 점수를 저장한다. 최종 각 축에 최소 하나의 허용된 사용자 근거가 남았는지 검증하고, 없으면 어떤 평가/진행 write도 하기 전에 결과를 거부해야 한다. 선택 턴 scope에서는 다른 사용자 턴의 ID도 허용 근거가 아니다.

인용문이 실제 원문과 같은 것에 더해 rationale이 해당 축에 맞는 관찰인지 실제 응답을 검토한다. 생성 교정의 original도 실제 학습자 텍스트에 존재하는지 확인하는 것이 필요하다. 프롬프트나 임의의 nonempty 문자열만으로 의미 품질을 통과 처리하지 않는다.

기존 전체 이력 재검사와 변경 시 409 경계를 유지한다. 선택 평가도 선택 발화가 편집/삭제되거나 대화가 비활성화되면 오래된 결과를 현재 발화에 표시하지 않는다. UI 요청 취소, 재시도, 초안 보존과 저장형 결과의 reload 동작을 명시한다.

## 실제 실연동 검증 시나리오

대상은 `http://dodonet.iptime.org:13000/`이고 실제 Supabase·OAuth AI를 사용한다. 한 worker로 직렬 실행하고 테스트별 소유 계정/fixture를 정리한다.

1. **턴별 귀속과 이후 정정:** 고정 미션에서 assistant가 숙박 일수를 묻고 사용자가 과거 시제 등 중요한 오류가 든 답을 한다. 다음 턴에는 정정된 문장을 말한다. 앞선 사용자 턴을 선택 평가했을 때 원문과 수정은 앞선 턴에 귀속되고, 이후 정정 턴을 성공 증거로 쓰지 않는지 확인한다. 선택 결과의 다섯 축 또는 해당 scope의 명시적 평가 항목과 한국어 근거를 실제 내용으로 검토한다.
2. **상호작용과 문법 분리:** 질문에 답하는 문법 오류 문장과 문법적으로 맞지만 질문과 무관한 답을 별도 소유 대화에서 비교한다. 임의 점수 차이를 단정하는 assertion보다 각 interaction rationale이 실제 질문/답의 관련성을 설명하는지, grammar rationale이 실제 문법을 다루는지 검토한다.
3. **자연스러운 대안:** 뜻은 전달되지만 상황에 어색한 표현을 사용해 원문 보존과 자연스러운 대안이 어휘·표현 피드백에 연결되는지 확인한다. 단순 target vocabulary 포함 여부로 대체하지 않는다.
4. **부작용 경계:** 턴 평가 전후 messages, mission_run 상태/score/stars, step progress, mission_evaluations, reward unlock, XP를 비교한다. 전체 미션 평가 전에는 턴 평가가 목표 완료나 보상을 만들지 않아야 한다. 이어 전체 평가 버튼을 눌러 다섯 축 및 기존 완료/보상 멱등성이 동작하는지 확인한다.
5. **다섯 축 실제 저장 복원:** 기존 evaluation-axes.spec.ts를 새로운 다섯 축으로 보강하고 각 score/evidence/rationale API→DB→UI→reload 일치를 확인한다. 기존 결과를 이 테스트용으로 덮어쓰지 않는다.
6. **과거 데이터 호환:** 기존 네 축 object와 axes 배열 형식을 각각 가진 소유 fixture를 복원해 과거 label·score·총점이 그대로이고 interaction 점수를 만들어 내지 않는지 확인한다. 실제 fixture를 사용할 경우 테스트 소유 데이터에만 한정한다.
7. **권한·상태·실패:** 다른 계정 대화/선택 ID, 같은 대화 assistant ID, 존재하지 않는 ID, 편집/삭제된 ID, streaming 중 요청을 거부하고 평가 실패 시 입력 초안을 보존한다. 공급자 실패와 결과 유실 재시도의 중복/복원 정책을 검증한다.
8. **근거 validation 계약:** 생성 결과의 모든 evidence ID가 assistant/외부/없는 ID인 경우, 또는 선택 턴 이외의 ID뿐인 경우 최종 점수 저장 전에 실패해야 한다. 이것은 순수 정책 계약 테스트로 분리하고 실제 실연동 happy path와 합쳐 판정한다.

위 시나리오는 제안이며 PASS 결과가 아니다. 다섯 축만 추가하고 선택 턴 동작을 빠뜨리거나, 선택 교정만 추가하고 11.2의 독립 축과 근거를 빠뜨리면 LEARN-05는 계속 PARTIAL이다.


## 후속 구현·검증 결과

위 내용은 구현 전 감사 기록이다. 후속 작업에서 다섯 독립 축과 축별 피드백/유효 사용자 근거 검증, version2 가중치 저장, 선택 사용자 발화의 읽기 전용 임시 평가를 구현했다. 선택 턴 이후의 정정 발화나 이전 오류를 해당 턴의 점수 근거로 사용하지 않으며, 생성 후 문맥을 재확인한다. 없는 최종 근거는 어떤 평가/진행 저장보다 먼저 거부한다. 과거4축/총점은 그대로 유지한다.

실제5축/실패→재평가 성공2개(96822의 통과 부분), 과거2형식/선택턴/기존 도움말5개(38990), 선택 전후 발화 분리 확장1개(95751), 완료/보상 회귀2개(46391), 상호작용 관련성 대조1개(21095)를 각각 확인했다. 중복 실행이므로 고유 개수로 합산하지 않는다. 문법적으로 올바른 두 문장에서도 질문에 답한 경우와 무관한 경우의 interaction96/15와 실제 질문 근거를 확인했다. 자연스러운 “I’d like…” 대안, 원문 오류의 wants→want 수정과 이후 올바른 발화의 오류 없음도 실제 응답으로 검토했다.

생성 중 문맥 변경의 409 경계는 지연 생성/재조회 순서 계약으로 검증했다. 실제 공급자를 동기화해 변경 409를 유발한 브라우저 시나리오로 주장하지 않는다. 악성 근거 ID의 저장 전 거부도 순수 계약과 실제 정상 생성/저장 증거를 함께 사용한다. 저장형 전체 평가와 임시 선택턴 평가의 reload 정책은 다르며 UI에 구분해 안내한다. 실제 결과·실패 수정 이력·보고서 경로는 live E2E 진행 원장을 따른다. LEARN-05는 이 증거로 VERIFIED이며 LEARN-02 자동 목표 추적을 완료한 것으로 확대하지 않는다.
