# 업무 관계 검증

직접 호출했다면 [역할 지침](../../AGENT.md)을 먼저 읽는다.

입력: focus 영역/질문 하나, 후보 관계, 관련 근거. 출력: audit.json, 새 evidence.jsonl, claims.json 수정 제안, result.json.

[반환 계약의 audit 형식](../../../../contracts/handoff.md#auditjson-최소-형식)을 따른다. outputMode=delta이며 claims.json은 이번 제안만 포함한다. 메인이 기존 누적 claims/evidence와 병합한다.

1. [모델 계약](../../../../contracts/model.md)을 읽는다. focus가 없으면 영향이 큰 미확인 경계/충돌/대표 시나리오 중 하나를 선택하고 이유를 기록한다.
2. 명령/요청 → 판단 규칙 → 상태 변경 → 데이터 쓰기 → 이벤트/외부 호출 중 질문에 필요한 구간만 추적한다.
3. 클라이언트와 서버 계약, 발행과 구독, 설정의 실제 대상이 서로 맞는지 비교한다. 호출 방향과 응답 정보 흐름을 구별하고 관계 label에 의미를 쓴다.
4. 한쪽 계약만 있으면 그 사실을 기록하고 끝까지 연결된 관계로 확정하지 않는다. 실행되지 않는 코드인지 정적 분석으로 판별할 수 없으면 미확인으로 둔다.
5. 문서와 구현의 충돌은 어느 한쪽을 삭제하지 않는다. stakeholder 확인이 필요하면 구체적인 질문을 작성한다.
6. 테스트는 확인할 주장과 연결된 경우에만 읽는다. 기본 조사에서 대상 레포의 스크립트/테스트/배포는 실행하지 않는다.

완료 기준: 연결별 지지/충돌/미확인 판정, 방향, 근거 위치와 다음 확인 조건이 있다. 조사 예산이 끝나면 확인한 구간까지 저장한다.
