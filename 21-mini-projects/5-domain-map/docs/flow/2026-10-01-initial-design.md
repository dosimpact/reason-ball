# 2026-10-01 — Domain Map 초기 설계와 분석 프롬프트

## 배경

사용자는 여러 광고 도메인 레포를 큰 블록부터 이해하고, 팀의 진행 작업과 영향 범위를 지속적으로 공유할 지도를 원한다. LikeC4를 선택했고, 1개~수십 개 레포를 AI가 점진적으로 분석할 프롬프트 구성을 요청했다.

## 결정과 이유

- DM-001/002/010: 전체를 얕게 조사한 뒤 선택적으로 상세화한다. 초기부터 한 레포의 구현에 몰입하는 편중을 막는다.
- DM-005/009: 근거·주장·중간 모델·LikeC4를 분리한다. 지도만으로 추론과 검증 상태를 관리하지 않는다.
- DM-011: 상태와 조사 큐를 파일로 보존하고 변경된 근거를 재확인한다. 한 세션의 컨텍스트에 의존하지 않는다.
- DM-003/008: 현재 작업과 소유권을 별도 모델로 둔다. 레포 분석만으로 현재 담당 업무를 확정할 수 없다.

## 영향받은 stock

- [비즈니스 설계](../stock/business-design.md): 목적, 요구 ID, 성공 기준
- [시스템 설계](../stock/system-design.md): 조사 루프, 저장 계약, 검증과 갱신

## 산출물과 검증 범위

README, stock 2종, 실행 프롬프트, YAML 입력 예시, 이 flow를 작성했다. apb-templates의 설계 틀을 참고하되 저장소 지시에 따라 stock/flow 경로를 사용했다.

LikeC4 공식 저장소/모델/views/CLI 문서를 확인했다. Markdown 5개 파일의 상대 링크와 코드 펜스 검사에서 오류 0개를 확인했다. 예시 YAML 파서 검사는 로컬 Python/Node YAML 모듈 부재로 NOT RUN이다. 실제 회사 레포 분석, LLM 실행 품질, LikeC4 설치/DSL 생성/build, 브라우저 검증도 NOT RUN이다. 현재는 설계 산출물이며 실행 가능한 앱을 완성했다고 볼 수 없다.

## 후속

실제 입력 2~3개로 prompt pilot → 근거와 ID 계약 보정 → LikeC4 최소 앱 → 변경분 갱신 → 업무 데이터 연결 순서로 검증한다. 런타임 구현 시 별도 작업 브랜치에서 루트 pnpm workspace를 사용한다.
