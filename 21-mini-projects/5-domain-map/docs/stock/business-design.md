# Domain Map 비즈니스 설계

> **Summary**: AI 기반 점진적 도메인 발견과 팀의 공통 지도
>
> **Author**: Codex / 사용자 요구 기반
> **Created**: 2026-10-01
> **Status**: Draft — 요구 방향 확인, 운영 세부안 제안

## 목적

DM-001: 입력된 1개~수십 개 저장소를 바탕으로 기업의 업무 능력, 시스템 책임, 주요 관계를 지속적으로 이해한다. 첫 결과는 코드 상세보다 큰 블록과 업무 언어에 집중한다.

DM-002: 한 번의 실행으로 전체 도메인 이해가 끝났다고 주장하지 않는다. 입력 범위 내 조사 진척과 미확인 영역을 보이게 하고, 다음 실행이 이전 결과를 이어받는다. 입력에 없는 서비스와 수작업 업무도 외부 경계 또는 질문으로 보존한다.

DM-003: 팀원이 전체 구조, 책임 주체, 현재 변경의 영향 영역을 같은 지도에서 파악하도록 한다. 현재 작업은 저장소만으로 확정할 수 없으므로 이슈/PR/수동 상태 입력을 별도 정보원으로 둔다.

## 사용자가 답을 얻을 질문

- 이 회사의 광고 업무는 어떤 큰 영역으로 구성되는가?
- 각 영역은 어떤 레포와 시스템으로 구현되어 있는가?
- 영역 사이에 어떤 업무 정보가 전달되는가?
- 어떤 설명이 확인된 사실이고 무엇이 가설인가?
- 지금 누가 어떤 영역을 바꾸고 있으며 다른 작업과 어디에서 만나는가?
- 마지막 조사 이후 무엇이 바뀌었고 어디를 다시 확인해야 하는가?

## 범위와 단계

| 단계 | 목표 | 산출물 |
| --- | --- | --- |
| 초기 | 전체 입력을 얕게 훑어 누락을 드러낸다 | 레포 목록, 큰 업무 영역 후보, 주요 관계, 질문 |
| 확장 | 중요한 경계와 업무 시나리오를 검증한다 | 영역별 상세, 근거, 용어 충돌, 외부 경계 |
| 지속 | 변경에 영향받은 지식을 재검증한다 | 변경 내역, 오래된 근거, 갱신된 지도 |
| 팀 sync | 현재 업무를 구조에 연결한다 | 작업·담당자·상태·영향 영역·최신성 |

현재는 설계와 프롬프트만 존재한다. 위 단계의 분석/시각화 기능은 구현 계획이다.

## 모델링 원칙

- DM-004: 레포와 도메인은 다대다 관계다. 디렉터리 이름이나 서비스 개수로 도메인 수를 결정하지 않는다.
- DM-005: 관찰된 구현, 문서의 주장, 업무 담당자의 확인, 분석자의 추론을 구분한다. 코드와 문서 충돌을 자동으로 한쪽의 승리로 처리하지 않는다.
- DM-006: 첫 화면은 기본 5~12개 큰 블록을 목표로 하되, 실제 구조를 숫자에 맞춰 합치지 않는다. 많으면 계층과 별도 view로 나눈다.
- DM-007: 구현 상태(as-is)와 미래 제안(to-be)은 별도 view로 관리한다.
- DM-008: 시스템 owner, 코드 리뷰 담당자, 현재 작업 assignee는 다른 관계다. 커밋 작성자를 업무 담당자로 단정하지 않는다.

## 성공 기준

1. 모든 입력 레포에 조사 상태가 있고, 접근 실패/보류/미조사를 누락하지 않는다.
2. 지도에 나타나는 블록과 연결은 근거 또는 명시적인 가설 ID로 추적된다.
3. 새 세션이 기존 기록만으로 다음 조사 항목을 선택할 수 있다.
4. 근거가 바뀌면 관련 주장과 지도가 재검토 대상으로 표시된다.
5. 담당자가 대표 업무 흐름을 따라가며 잘못된 경계와 용어를 수정할 수 있다.
6. 현재 작업 데이터가 없으면 '작업 정보 없음'으로 보이며 임의로 채우지 않는다.

전체 도메인 이해도를 임의의 백분율로 표시하지 않는다. `초기 조사 완료 레포 / 입력 레포`, `근거 있는 관계 / 전체 후보 관계`, `확인 완료 질문 / 등록 질문`을 구분해서 표시한다. 이 지표는 의미적 완전성을 보장하지 않는다.
