## 목표

- `lightweight-charts`를 사용해 엘리어트 파동이론을 실전 매매까지 연습할 수 있는 인터랙티브 튜토리얼을 구현한다.
- 단순 설명형 페이지가 아니라, 사용자가 실제 캔들 차트 위에서 파동을 직접 선택하고 검증받는 학습 경험을 만든다.
- MVP에서는 Elliott Wave 전체 이론을 다루지 않고, Impulse Wave와 1-2-3파 매매 연습에 집중한다.

## 핵심 UX

- 화면 왼쪽에 튜토리얼 챕터와 각 챕터의 튜토리얼 유닛을 볼 수 있는 사이드바를 표시한다.
- 화면 중앙에 실제 OHLC 캔들 차트를 표시한다.
- 연습 모드에서 사용자는 차트 위의 특정 캔들을 클릭해서 Wave 1, 2, 3, 4, 5 지점을 순서대로 지정할 수 있다.
- 선택된 파동은 숫자 라벨과 연결선으로 시각화한다.
- 사용자가 선택을 완료하면 엘리어트 파동의 규칙을 자동 검증한다.
- 정답을 바로 보여주기보다 사용자의 선택 결과와 규칙 위반 여부를 먼저 보여준다.
- 필요할 때 정답 또는 예시 파동을 확인할 수 있도록 한다.

## 튜토리얼 구조

- 튜토리얼은 챕터 아래의 독립적인 유닛으로 구성한다. 각 유닛은 자체 학습 목표, 설명, 차트 시나리오, 허용 동작, 완료 조건을 가진다.
- 유닛은 `이론` 또는 `연습` 모드를 가진다. 이후 다른 학습 방식을 추가할 수 있도록 모드별 데이터와 진행 로직을 분리한다.
- 초기 유닛의 학습 주제와 도메인 설명은 [docs/tutorials/](docs/tutorials/INDEX.md)에서 관리한다. 챕터별 배치와 유닛 세분화는 상세 설계에서 정한다.

## 튜토리얼 모드

- 이론 모드: 유닛이 순서 있는 설명 단계들을 가진다. 학습자가 `Next`를 누르면 다음 단계의 설명, 차트 데이터 공개 범위, 파동·Fibonacci 표시 등 필요한 화면 상태가 함께 바뀐다. 마지막 단계에서는 유닛 완료를 표시한다.
- 연습 모드: 유닛이 과제와 차트 시나리오를 제공한다. 학습자가 직접 파동 선택, 검증, 매매 가격 설정, Replay 등 해당 유닛이 허용한 동작을 수행하고 결과·피드백을 확인한다.
- 매매 연습 유닛은 `TradePlan` 작성·확정 → Replay 또는 시간 경과 → `TradeEvaluation` 확인까지 하나의 학습 흐름으로 제공한다.
- `Next`(이론 단계 이동)와 `Next Candle`(Replay의 미래 캔들 공개)은 별도 동작으로 취급한다.
- 두 모드 모두 공통 차트와 사이드바를 사용하되, 진행 상태와 완료 기준은 유닛별로 정의한다.

## 튜토리얼 유닛 모델 및 디렉터리

- `Chapter`: 안정적인 ID, 제목, 설명, 정렬 순서, 소속 유닛 ID 목록을 가진다.
- `TutorialUnit`: 공통 식별 정보와 모드별 설정을 가진다. 이론 유닛은 순서 있는 단계, 연습 유닛은 과제·허용 동작·완료 조건을 가진다.
- 유닛별 콘텐츠·시나리오·설정은 해당 유닛 디렉터리에 함께 두고 다른 유닛의 내부 파일을 직접 참조하지 않는다.
- 공통 차트, 파동 검증, Fibonacci, Replay, 매매 계산 및 UI는 재사용 모듈로 분리한다.
- 챕터·유닛 목록은 별도 등록 정보에서 구성하여 사이드바와 유닛 진입에 사용한다.
- 상세 모델과 디렉터리 구조는 `docs/stock/system-design.md`를 기준으로 한다.

## 디렉터리 구조와 FSD 경계

- FSD의 `app → pages → widgets → features → entities → shared` 책임과 아래 방향의 의존 규칙을 사용한다. Next.js가 `src/pages/`를 라우트로 해석하므로 이 프로젝트의 FSD pages 역할은 `src/views/`로 이름을 바꾼다.
- `src/app/`은 Next.js 라우트·전역 Provider·얇은 API 진입점, `src/views/`는 화면 조립, `src/widgets/`는 사이드바·차트 작업 영역처럼 독립적인 큰 화면 블록을 담당한다.
- `src/features/<도메인-행동>/`은 이론 진행, 파동 선택, Fibonacci 해석, 계획 확정, 캔들 공개, 평가 확인 등 학습자의 행동별로 나눈다. `src/entities/<도메인>/`은 TutorialUnit, Candle, Wave, TradePlan, TradeEvaluation의 모델·순수 규칙을 담당한다.
- `src/shared/`에는 shadcn/ui 기반 공통 UI와 범용 차트 어댑터만 둔다. Binance 조회·캐시와 계획 보존처럼 서버에서만 실행할 코드는 `src/server/`에 두고 클라이언트 슬라이스에서 직접 import하지 않는다.
- 유닛 콘텐츠는 `src/entities/tutorial/content/units/<unit-id>/`에 독립적으로 둔다. 새 유닛은 자체 정의·시나리오·테스트와 카탈로그 등록으로 추가하며 다른 유닛의 내부 파일을 참조하지 않는다.
- 슬라이스 간 참조는 공개 `index.ts`를 통하고 같은 계층의 다른 슬라이스 내부를 직접 import하지 않는다. 함수는 SLAP에 따라 한 추상화 수준을 유지한다. 화면 흐름의 조정과 Binance 응답 파싱·캐시·가격 계산을 한 함수에 섞지 않는다.

## 차트 데이터 소스

- 차트 시나리오는 `dummy`와 `binance` 소스를 선택할 수 있다. 유닛의 학습 로직과 차트 UI는 데이터 출처에 의존하지 않는다.
- 더미 데이터는 재현 가능한 고정 OHLC 시나리오로 제공한다.
- Binance 소스는 공개 Spot 캔들 데이터를 서버 측 어댑터에서 조회하고 공통 `Candle` 형식으로 변환한다. 실제 주문·계정 연동은 하지 않는다.
- Binance 조회 결과는 심볼·간격·시간 범위 등 요청 조건별로 캐시한다. 과거 확정 캔들과 최근 미완성 캔들의 갱신 정책을 구분한다.
- 연습과 Replay가 시작되면 해당 시나리오의 캔들 구간을 고정해 진행 중 데이터 갱신으로 정답·결과가 바뀌지 않게 한다.
- 소스·캐시와 무관하게 Replay에서 아직 공개하지 않은 미래 캔들과 정답 데이터는 학습자에게 전달하지 않는다.

## 튜토리얼 도메인 지식

학습 내용은 [튜토리얼 문서 목차](docs/tutorials/INDEX.md) 아래에서 Lesson별로 관리한다.

## Elliott Wave 검증 기능

- 도메인 지식의 3대 규칙을 자동 검증한다.
- 각 규칙은 별도의 validator 함수로 분리한다.
- 검증 결과는 `pass`, `fail`, `reason` 형태로 반환한다.

## 파동 선택 기능

- 사용자가 차트의 캔들을 클릭하면 해당 시점의 time과 price를 저장한다.
- 선택 순서는 Wave 1 → Wave 2 → Wave 3 → Wave 4 → Wave 5로 진행한다.
- 선택된 포인트는 차트 위에 `1`, `2`, `3`, `4`, `5` 라벨로 표시한다.
- 각 파동 포인트 사이에 연결선을 그린다.
- 잘못 선택한 포인트를 undo하거나 전체 reset할 수 있어야 한다.

## 차트 오버레이

- Series Marker를 활용해 Wave 번호를 표시한다.
- 파동 연결선은 custom primitive 또는 적절한 overlay 방식으로 구현한다.
- Fibonacci retracement와 extension도 차트 위에 시각화한다.
- 차트의 zoom, pan과 오버레이가 자연스럽게 함께 동작해야 한다.

## Fibonacci

- 도메인 지식에 정의한 retracement와 extension을 차트에 표시한다.
- 학습용 후보 영역이라는 점을 UI에 표현한다.

## 매매 연습

- 도메인 지식에 정의한 Wave 3 진입 흐름을 연습한다.
- 사용자가 Entry, Stop Loss, Target을 직접 지정할 수 있게 한다.
- Stop Loss와 Target의 참고 위치를 안내한다.
- 선택한 카운팅의 무효화 지점과 사용자가 설정한 Stop Loss를 함께 표시해 두 기준의 차이를 학습한다.
- 계획 확정 후 Replay를 진행해서 이후 가격 움직임을 확인한다.

## TradePlan 및 TradeEvaluation

- 학습자는 Replay나 사후 시장 데이터 확인 전에 파동 카운팅, Fibonacci 근거, Entry·Stop Loss·Target, 무효화 조건, 각 판단 이유를 `TradePlan`으로 작성하고 확정한다.
- 계획에는 스키마 버전, 유닛·시나리오·데이터 출처, 작성 시각, 의사결정 기준 시각(`asOf`), 공개된 마지막 캔들, 데이터 스냅샷 식별자를 포함한다.
- 확정된 계획은 수정하지 않는다. 계획을 바꾸려면 새 버전의 계획을 작성해 이전 계획과 연결한다.
- `TradeEvaluation`은 계획을 참조해 이후 관측 구간, 진입·손절·목표 도달, 청산 가격·R 결과, 카운팅 규칙 적용, 판단별 피드백과 평가 상태를 기록한다. 원본 계획과 평가 결과는 별도로 보존한다.
- 평가 경로는 고정 시나리오의 Replay 평가와, Binance 소스의 시간이 지난 뒤 확정 캔들을 다시 조회하는 사후 평가를 지원한다. 후자는 이후 데이터가 충분할 때 학습자가 다시 확인할 수 있게 한다.
- 한 캔들에서 Stop Loss와 Target이 모두 닿는 등 OHLC만으로 순서를 알 수 없는 경우에는 임의로 승패를 정하지 않고 `판정 불가`로 표시한다. 체결·수수료·슬리피지 가정은 상세 설계에서 정의한다.
- 계획과 평가 데이터는 각각 JSON Schema로 형식을 검증하고, 파동 규칙·시점·성과 판정은 별도 도메인 로직으로 검증한다.

## Replay 기능

- 초기에는 미래 캔들을 숨긴다.
- 사용자가 `Next` 버튼을 누를 때마다 다음 캔들 1개 또는 일정 개수를 공개한다.
- Play / Pause 기능을 제공해 자동 진행도 가능하게 한다.
- Replay 도중 Entry, Stop Loss, Target 도달 여부를 추적한다.
- 5파 완료가 관찰되는 시나리오에서는 조정 가능성을 바탕으로 청산 여부를 판단하고, 선택의 근거를 결과 피드백에서 확인한다.
- 미래 데이터를 사용자에게 미리 노출하지 않는다.

## 결과 화면

- 매매 종료 또는 사후 평가 후 원본 TradePlan과 TradeEvaluation을 나란히 확인하고, 다음 정보를 표시한다.
- Entry Price
- Stop Loss
- Target
- 실제 Exit Price
- 손익률
- Risk Reward Ratio
- 결과를 R 단위로 표시
- 사용자의 Elliott Wave 카운팅이 유효했는지 여부
- 어떤 규칙을 잘 적용했고 어떤 부분이 틀렸는지 피드백

## 학습 피드백

- 단순히 `정답 / 오답`만 표시하지 않는다.

- 가능한 경우 사용자가 다시 수정해서 재검증할 수 있도록 한다.

## MVP 범위

- 상승 Impulse Wave만 우선 지원한다.
- 1-2-3-4-5 구조만 지원한다.
- ABC, Zigzag, Flat, Triangle, Diagonal은 구현하지 않는다.
- 자동 Elliott Wave 탐지 기능은 구현하지 않는다.
- 사용자가 직접 파동을 선택하고 검증받는 경험에 집중한다.
- 실제 주문 기능은 구현하지 않는다.

## 구현 원칙

- 도메인별 FSD 슬라이스와 아래 방향의 의존 규칙을 지킨다. 새로운 기능은 사용자 행동과 도메인 책임을 기준으로 배치한다.
- SLAP(Single Level of Abstraction Principle)을 지킨다. 상위 함수는 같은 수준의 단계들을 호출하고 저수준의 계산·변환·판정은 가능한 한 입력과 출력이 명확한 순수 함수로 분리한다. 외부 API·저장·시간 조회처럼 부작용이 필요한 작업은 별도 경계 함수로 둔다.
- Elliott Wave 비즈니스 규칙과 차트 렌더링 로직을 분리한다.
- 차트 라이브러리 의존 코드가 validator 로직에 섞이지 않게 한다.
- validator 함수는 unit test가 가능하도록 pure function으로 작성한다.
- tutorial lesson 데이터와 UI 컴포넌트를 분리해 이후 Lesson 추가가 쉽게 한다.
- 한 유닛의 콘텐츠·시나리오·설정을 수정해도 다른 유닛의 정의에 영향을 주지 않도록 한다.
- 하드코딩된 특정 차트 데이터에만 동작하지 않게 구현한다.

## 구현 방법 — Walking Skeleton

- 처음에는 작은 사용자 시나리오 하나가 화면 → API → 데이터 조회·보존 → 도메인 계산 → 화면 결과까지 실제로 이어지도록 구현한다. 이후 기능은 이 작동 경로를 유지하며 얇은 단위로 확장한다.
- 첫 경로는 더미 캔들을 사용하는 연습 유닛 1개로 시작한다: 사이드바에서 유닛 선택 → 캔들 표시 → 최소 파동 선택 → 간단한 TradePlan 확정·보존 → 다음 캔들 공개 → TradeEvaluation 결과 표시. 각 단계는 최종 계약의 작은 부분을 사용한다.
- 첫 경로에도 유닛 카탈로그, 공통 Candle 계약, 모드 경계, 계획·평가의 분리와 미래 데이터 차단을 포함한다. 화면만 연결한 임시 데모를 완료로 보지 않는다.
- 첫 경로가 실제로 작동하고 검증된 뒤 이론 단계, 전체 파동 규칙, Fibonacci, 매매 계산, Binance 어댑터·캐시, 사후 평가와 추가 유닛을 순차적으로 붙인다. 순서는 통합 위험과 학습 가치에 따라 조정할 수 있다.
- 각 확장 단계마다 관련 순수 계산 테스트, Storybook UI 상태, Bruno 실제 HTTP 계약, Playwright 사용자 흐름을 변경 범위에 맞춰 확인한다.

## 완료 조건

## 파동이론 전략 실행 모니터링 (Strategy Execution Monitoring)

### 목적과 제공 경로 — SM-002

파동이론 전략 실행 모니터링을 튜토리얼 연습과 **독립적인 전략 작업 공간**에서 모두 제공한다. 사용자는 챕터·유닛 선택이나 과제 수행 없이 **검증 방식·시장 데이터 선택 → 파동 분석·계획 작성 → 계획 확정 → 백테스팅 또는 포워드 테스팅**을 진행할 수 있다.

- **튜토리얼 경로**: 기존 연습 안에서 계획·모니터링·평가를 학습한다.
- **독립 경로**: 별도 페이지에서 자신의 전략을 작성하고 저장된 전략의 실행 상태를 확인한다. 튜토리얼 진도·정답·수료 조건을 요구하지 않는다.
- **구현 상태**: 연습 내 모니터링(SM-001)과 아래 독립 페이지(SM-002/SM-003)가 구현되어 있다. 현재 계약은 stock, 실행 증거는 [독립 전략 검증](docs/validation/standalone-strategy.md)을 기준으로 확인한다.

### 전용 페이지와 사용자 흐름

| 경로 | 역할 | 주요 내용 |
| --- | --- | --- |
| `/monitoring` | 전략 목록 | 새 계획 만들기, 저장된 전략 재개, 시장·시간봉·실행 상태·마지막 관측 시각 확인 |
| `/monitoring/new` | 계획 작성 | 백테스트/포워드 방식·데이터 소스·종목·시간봉·기준 시점 선택, 차트 파동 기준점 선택, 진입·손절·목표·무효화 조건·판단 이유 작성 |
| `/monitoring/[strategyId]` | 전략 상세·검증 | 확정 원본, 실행별 백테스트/포워드 결과, 차트·손익·이벤트, 재생/감시 제어, 중단·평가·JSON 내보내기 |

1. 메인과 공통 내비게이션에서 **전략 모니터링**으로 진입한다. 목록이 비어 있으면 새 계획 작성으로 안내한다.
2. 백테스트는 과거 기준 시점, 포워드는 현재 최신 확정봉을 기준으로 Binance 실제 확정봉과 캐시를 이용해 계획을 세운다. 더미 데이터도 선택해 동일 흐름을 재현할 수 있다. 데이터 소스는 명확하게 표시하고 오류 시 임의 대체하지 않는다.
3. 초안을 저장하고 다시 열어 수정할 수 있다. `DRAFT`는 작성 상태이며 실행 상태 머신의 `PENDING`과 구분한다.
4. 확정 시 `TradePlan` JSON에 데이터 출처, `asOf`, 스냅샷 식별자, 파동 기준점, 진입·손절·목표, 무효화 규칙·정책과 이유를 고정한다. 확정 이후 봉만 실행 판정에 사용한다.
5. 확정된 전략의 상세 페이지에서 과거 고정 구간의 백테스트를 실행하거나 새 확정봉을 기다리는 포워드 감시를 시작한다. 과제·퀴즈·학습 단계 없이 계획과 실행을 직접 비교한다.
6. 저장된 전략은 목록에서 다시 열 수 있다. 수정은 새 revision으로 보존하고 이전 계획·실행 이벤트·평가를 덮어쓰지 않는다.

### 백테스팅과 포워드 테스팅 — SM-003

두 검증 방식은 동일한 계획 검증·상태 머신·체결 정책을 사용하되 데이터의 기준 시점과 관측 방식이 다르다.

**확정 요구사항**: 독립 전략 페이지는 아래 두 흐름을 모두 제공한다. 백테스트 완료를 포워드 테스트의 필수 선행 조건으로 두지 않는다. 사용자는 계획 작성 시 검증 방식을 선택하며, 확정 후 방식을 바꾸려면 해당 시점의 데이터로 새 revision을 검토·확정한다.

- **계획 → 백테스팅 → 평가**: 과거 기준 시점·관측 구간 선택 → 공개된 과거 차트로 계획 작성·확정 → 이후 봉 재생/일괄 실행 → 계획 대비 실행 이벤트·손익 평가 및 JSON 저장.
- **계획 → 포워드 테스팅 → 평가**: 최신 확정봉으로 계획 작성·확정 → 이후 새 확정봉 대기·모의 실행 → 관측 중 잠정 평가 → 전략 종료 또는 사용자 중단 시 결과 보존.
- **백테스트 후 포워드 전환**: 백테스트의 판단 근거를 참고하되 현재 시장에 맞춰 새 revision을 확정한다. 이전 백테스트 run과 이후 포워드 run은 같은 전략 이력에서 방식·기준 시점·계획 변경점을 구분해 확인한다.

| 구분 | 백테스팅 | 포워드 테스팅 |
| --- | --- | --- |
| 기준 시점 | 사용자가 선택한 과거 확정봉 | 계획 확정 시점의 최신 확정봉 |
| 계획 작성 화면 | 기준 시점까지의 캔들만 공개 | 확정 순간까지 알려진 캔들만 공개 |
| 실행 데이터 | 기준 시점 이후의 고정된 과거 구간 | 계획 확정 이후 실제로 새로 마감된 봉 |
| 실행 방식 | 한 봉 재생·자동 재생 또는 전체 구간 일괄 실행 | 새 봉 조회·60초 자동 감시, 새 봉이 없으면 대기 |
| 종료·결과 | 설정 구간 완료 또는 전략 종결, 결과·이벤트·미청산 여부 표시 | 전략 종결·사용자 중단, 관측 시점까지의 잠정 결과 표시 |

- **독립 실행 기록**: 전략의 특정 `planId`·revision 아래에 `runId`, 방식(`BACKTEST`/`FORWARD`), 데이터 출처·기간·스냅샷, 체결 정책 버전, 시작·종료·마지막 관측 시각, 상태·이벤트·평가를 보존한다. 방식별 결과를 덮어쓰지 않는다.
- **동일 계획의 비교**: 확정된 가격·규칙은 재사용할 수 있다. 포워드는 계획 확정 이후 새로 생긴 봉만 대상으로 한다. 이미 지난 구간을 재생한 결과를 포워드로 표시하지 않는다. 과거 백테스트 계획을 현재 시장에 적용하려면 현재 공개 데이터로 다시 검증·확정한 새 revision을 만들고 연결한다. 가격·시점·스냅샷이 달라지면 동일 조건 실험으로 표현하지 않는다.
- **데이터 계약**: 백테스트는 Binance 과거 데이터+캐시 또는 더미 fixture를 고정하고 식별자와 해시를 저장한다. 포워드는 Binance 최신 확정봉+캐시를 사용한다. 더미의 순차 입력은 포워드 동작 검증용 시뮬레이션으로 표시하고 실제 시장 성과와 구분한다. API 오류·중복·누락·구간 초과를 표시하며 다른 소스로 조용히 대체하지 않는다.
- **미래 정보 차단**: 백테스트 계획 확정 전에는 선택한 기준 시점 이후 OHLC·판정 결과를 클라이언트에 전달하지 않는다. 실행 데이터는 기준 시점 이후 봉으로 제한한다. 같은 스냅샷·계획·정책은 재생과 일괄 실행에서 동일한 결과를 내야 한다.
- **실행 수명주기**: 작성 상태(DRAFT), 실행 제어 상태(대기·진행·일시정지·완료·오류), 매매 상태(PENDING/OPEN 등)를 구분한다. 백테스트 구간 종료 시 미진입은 EXPIRED, 보유 중이면 OPEN과 미청산 손익을 남기며 자동으로 익절·손절 처리하지 않는다. 포워드 감시 일시정지는 청산이나 실행 완료가 아니다.
- **평가 지표**: 실행별 진입·청산가, 무효화·중단 이유, 실현/미실현 손익과 R, 관측 기간·봉 수, 판정 불가 여부를 보여준다. 한 계획의 결과를 반복 표본의 승률이나 전략 수익성으로 일반화하지 않는다. 비교 화면은 방식과 데이터 구간을 함께 표시한다.
- **체결 가정**: 첫 버전은 기존 long 매수 스톱 진입, 수량 1, 수수료·슬리피지 0, 갭 시가 체결 정책을 공통 적용하고 결과에 명시한다. OHLC 내부 선후 불명은 INDETERMINATE로 남긴다. 비용 모델 확장이나 실제 주문 실행을 구현된 것으로 간주하지 않는다.

### 공통 모니터링 기능

- **JSON 기반 전략 상태 머신**: 확정된 `TradePlan`에 따라 `PENDING`, `OPEN`, `INVALIDATED_STOP`, `CLOSED_TP`, `CLOSED_SL`, `EXPIRED`를 추적한다. 수동 중단은 `ABORTED`, 봉 내부 선후 불명은 `INDETERMINATE`로 남긴다.
- **파동 무효화 감시**: 별도 무효화 가격과 명시적으로 확인한 3파 이후의 4파·1파 영역 침범 등 지원하는 규칙을 매 확정봉 판별한다. 자동 파동 카운팅을 가정하지 않는다.
- **자동 중단**: 기본 정책은 미진입 전략 취소·보유 포지션 모의 청산이다. 경고 전용 정책과 이유를 기록하는 수동 중단도 제공한다.
- **차트와 패널**: Entry·Stop Loss·Target·별도 무효화선을 표시한다. 파동 유효성(Healthy / Warning / Invalidated), 마지막 확정봉 종가, 미실현 손익·R·무효화 경계 이격도와 관측 시각을 표시한다.
- **기록과 평가**: 진입·청산·무효화·중단 이벤트에 시각과 이유를 기록하고 `TradeEvaluation`에 연결한다. 원본 계획·실행 이력·평가를 JSON으로 내보낸다. 기존 가격 조건 비교 평가와 실행 모니터링 결과를 구분한다.

### 실행 정책과 구조

- 튜토리얼과 독립 전략은 같은 순수 상태 머신·계획 검증·차트·모니터링 패널을 재사용한다. 독립 전략에 가짜 `unitId`나 튜토리얼 세션을 요구하지 않는다.
- 독립 전략 ID와 저장 수명주기를 별도로 두고 작성 상태, 데이터 스냅샷, 계획 revision, 방식별 runId, 실행 이력, 평가를 연결한다. 독립 StrategyPlan 계약을 사용하고 기존 튜토리얼 TradePlan JSON 계약은 유지한다.
- FSD의 도메인별 feature 경계와 SLAP을 유지한다. 상태 전이·무효화·손익 계산은 순수 함수, 데이터 조회·캐시·저장은 I/O 경계에 둔다.
- 첫 독립 버전은 기존 long 모의매매와 지원 종목·시간봉 범위를 사용한다. Binance 자동 감시는 사용자가 시작한 상세 화면에서 60초마다 새 확정봉을 조회한다. 화면을 닫으면 감시는 멈추고, 재방문 후 명시적으로 재개하여 마지막 관측 이후 봉을 순서대로 반영한다. 기존 최대 4000봉 조회 한도를 넘으면 한도 오류를 표시한다.
- 감시 일시 중지는 전략 취소·청산과 다르다. 재조회·새로고침으로 체결 이벤트가 중복되지 않아야 한다. 여러 화면에서 같은 전략을 조작할 때 서버가 충돌을 검증한다.
- GitHub Primer 라이트·다크 테마를 전용 페이지에도 적용한다. 실제 주문, 틱 감시, 서버 상시 백그라운드 감시는 이번 범위에 포함하지 않는다.

### Walking Skeleton과 완료 기준

먼저 **더미 데이터로 독립 초안 생성 → 과거 기준 시점에서 계획 확정 → 백테스트 한 봉 진행 → 상태·이벤트 저장 → 목록·상세 재방문 복원**까지 수직 흐름을 구현하고 검증한다. 이어서 재생·일괄 실행 결과 일치, Binance 과거 데이터+캐시, 새 확정봉 기반 포워드 감시·중단, revision·평가·내보내기를 연결한다.

- 튜토리얼 진입 없이 전용 목록·작성·상세 페이지에서 백테스트와 포워드 흐름을 각각 완료한다.
- 백테스트의 미래 정보 비노출과 재생/일괄 결과 일치, 포워드의 새 봉 대기·중복 방지·재개를 검증한다.
- 같은 전략의 여러 runId와 revision 결과가 섞이거나 덮어써지지 않고 방식·기간·정책을 포함해 복원·내보내기 된다.
- 초안과 확정 원본·revision·실행 기록이 새로고침과 서버 재시작 뒤 복원된다.
- 무효화 시 자동 취소·모의 청산, 수동 중단, 감시 중지·재개와 이벤트 중복 방지를 검증한다.
- Storybook으로 빈 목록·초안·실행 상태·오류·다크모드를, Bruno로 독립 전략 저장·조회·확정·중단 계약을, Playwright로 작성→모니터링→재방문 흐름을 검증한다. 순수 상태 머신 단위 검사와 기존 튜토리얼 회귀도 유지한다.

기존 [모니터링 구현 명세](docs/design/strategy-monitoring.md)와 [검증 기록](docs/flow/2026-09-27-strategy-monitoring.md)은 SM-001의 증거다. 독립 페이지 계획은 [SM-002 변경 기록](docs/flow/2026-09-27-standalone-monitoring-plan.md)에서 관리한다.

백테스트·포워드 검증 요구는 [SM-003 변경 기록](docs/flow/2026-09-27-backtest-forward-plan.md)에 기록한다.
