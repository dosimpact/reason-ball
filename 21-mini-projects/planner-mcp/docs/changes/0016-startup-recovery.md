# 초기 로딩과 실패 복구

날짜: 2026-09-15
상태: 코드 수정·생산 E2E 통과. 기존 개발 서버 복구는 별도 확인 필요.

## 증거와 원인 구분

- 사용자 보고: 프로젝트를 불러오는 중과 다시 불러오기만 표시된다.
- 기존 12개 E2E는 통과했으나 초기 SSE 실패·초기 API 실패·협업 요약 지연/실패를 검증하지 않았다.
- 기존 클라이언트는 SSE ready에서만 첫 refresh를 시작했다. 이 구조는 실시간 연결이 안 되면 API가 정상이어도 목록 조회를 시작하지 못한다.
- 실제 3100 서버 API는 프로젝트·협업 요약을 반환했지만 브라우저에는 로딩과 연결 복구 중이 표시됐다. 이후 버튼 클릭에도 API 요청이 없었으며 HMR WebSocket handshake 오류가 반복됐다. 따라서 실제 개발 서버에는 클라이언트 초기화 문제도 의심된다. HMR 오류만으로 그 내부 원인을 확정하지 않는다.

## 변경

- 초기 조회를 SSE와 독립적으로 예약하고 정리 시 예약을 취소한다.
- 협업 요약은 별도 요청으로 처리한다. 실패 시 경고와 재시도를 제공하며 목록·문서 조회를 막지 않는다.
- 사이드바에 수동 목록 새로고침을 제공한다.
- 브라우저 읽기 API 요청에 15초 대기 제한을 추가했다. 쓰기 요청의 재시도 계약은 변경하지 않았다.
- 현재 설계 11에 실패·복구 계약을 기록했다. 기존 데이터와 사용자 서버 프로세스를 변경/삭제하지 않았다.

## 검증

- 새 E2E 5개: 느린 요약과 목록 독립 표시, 빈 목록 안내, SSE 실패 시 초기 조회/선택, 초기 API 실패 후 재시도, 요약 실패 시 문서 조회와 재시도.
- 첫 추가 테스트 실행에서 Next route announcer와 앱 오류 alert가 함께 선택되는 문제가 있었다. 앱 main 영역으로 선택자를 한정하고 다시 실행했다. 제품 오류를 숨기는 assertion 삭제는 하지 않았다.
- codebase-memory로 경계와 제외된 테스트 범위를 확인했다. apb-playwright-e2e 절차에 따라 실제 브라우저 상태와 실패 자료를 확인했다.
- 생산 빌드 및 E2E 17개 PASS (47.5초), 전용 서버 `127.0.0.1:61884`와 임시 데이터를 사용한 뒤 정리했다. 이후 대기 제한은 읽기 요청에만 적용하도록 한정했다.
- 단위 테스트 89개, lint/typecheck PASS. 생산 E2E 통과를 실행 중인 개발 서버 복구 확인으로 간주하지 않는다.
- 사용자 서버의 HMR 오류·버튼 무반응은 프로세스를 정상 재시작한 뒤 같은 브라우저에서 확인해야 한다. 서버를 임의 종료하지 않았다.
