# 설계 입력·검토·구현 에이전트 인계

상태: 구현 기준. 실행 기본값은 [09](../tech-shared/planner-mcp/implementation.md), 추가 기능은 [10](10-completion.md)을 따른다.

## 역할과 책임

| 주체          | 책임                                                                                |
| ------------- | ----------------------------------------------------------------------------------- |
| 사용자        | 비즈니스 요구사항과 참고 자료 제공, 설계 검토·질문·승인                             |
| 설계 에이전트 | 요구사항 가공, 가정·질문 명시, MCP로 프로젝트와 설계 문서 생성·수정                 |
| Planner MCP   | 타입·내용 검증, 저장, 조회, 문서 상태 관리 및 UI 실시간 반영                        |
| 구현 에이전트 | 설계 완료 후 별도 에이전트로 MCP에서 프로젝트 인덱스와 설계 본문을 조회해 개발 수행 |

UI는 문서 조회·시각화·검토·질문·승인과 Flow 노드 편집을 담당합니다. 다른 타입의 설계 본문은 설계 에이전트가 작성합니다. 추가 편집 계약은 [10](10-completion.md)을 따릅니다.
구현 에이전트의 코드 실행·코드 생성은 Planner MCP 외부에서 수행합니다.

## 프로젝트 입력 보존

- 원본 요구사항과 참고 자료를 프로젝트에 연결해 이후 설계 판단의 근거를 확인할 수 있게 합니다.
- 입력은 프로젝트 부속 데이터 `sources`에 추가 보존합니다.
- source 필드: `id`, `kind`, `title`, `originalText`, `url`, `capturedAt`.
- 사용자가 전달한 원문과 AI의 요약을 구분하고 원문을 요약으로 덮어쓰지 않습니다.
- 문서가 참고한 입력은 source ID로 연결하는 방식을 사용합니다.
- Figma 링크와 전달받은 설명·추출 자료도 입력으로 연결합니다. API 수집은 [10](10-completion.md)에 따라 원문·파일 버전·수집 시각을 추가 보존합니다. 범용 원본 파일 첨부는 제공하지 않습니다.
- 직접 입력 URL은 수집 시각과 제공된 원문으로, Figma API 입력은 응답의 version·lastModified로 근거 시점을 구분합니다.

## 확정 사실·가정·질문

- 협업 홈·검토함과 질문 답변 기록은 [협업 UX](11-collaboration-ux.md)를 따른다. 질문 답변은 `questionId`가 연결된 의견으로 저장하고, AI의 설계 반영 및 질문 해결과 구분한다.

- 문서에서 확인된 사실, AI가 둔 가정, 미결정 질문을 구분합니다. 정보 부족을 사실처럼 채우지 않습니다.
- 타입별 content 외 공통 메타데이터로 `facts`, `assumptions`, `openQuestions`를 두는 방식을 사용합니다.
- 항목에는 식별자·내용·근거 source 참조를 둘 수 있습니다. 근거가 없는 내용은 확정 사실로 표시하지 않습니다.
- 사용자의 답변으로 질문이 해소되면 설계 에이전트가 해당 문서에 반영하고 해결 여부를 기록합니다.
- 문서 승인과 개별 가정의 사실 전환은 별개입니다. 승인만으로 가정을 사실로 바꾸지 않습니다.
- 구현에 영향을 주는 미결정 질문은 인계 시 명시합니다. blocking=true이고 resolved=false인 질문은 승인을 막으며 예외 승인 동작은 제공하지 않습니다.

## 문서 상태

작성과 사용자 승인을 분리하며 `draft → reviewed → approved` 상태를 사용합니다.
현재 전이 계약은 다음과 같습니다.

| 전이                         | 의미·주체                              |
| ---------------------------- | -------------------------------------- |
| 생성 → draft                 | 설계 에이전트가 초안 작성              |
| draft → reviewed             | 사용자가 검토 완료; 최종 승인과는 구분 |
| reviewed → approved          | 사용자가 개발에 사용할 설계를 승인     |
| reviewed/approved → 새 draft | 본문·설계 판단 변경으로 재검토 필요    |

- 승인 기록에는 승인자, 시각, 대상 문서 revision을 연결하는 방식을 사용합니다.
- AI의 생성·수정 호출만으로 사용자 승인이 부여되지 않도록 본문 저장과 상태 변경을 구분합니다.
- 사용자 인증은 제외합니다. UI의 로컬 사용자 이름으로 기록하며 반려 대신 의견과 새 초안으로 재검토합니다. 상태 변경은 UI API로만 노출합니다.
- 승인된 내용의 수정은 새 draft revision으로 처리하고 기존 승인 버전은 유지하는 방식을 사용합니다.
- 승인 버전은 자동 삭제하지 않으며 저장 경로는 [09](../tech-shared/planner-mcp/implementation.md)를 따릅니다.
- 저장소 개발 문서의 `초안/검토 중/확정` 표기와 제품이 관리하는 문서 상태는 별도 계약입니다.

## 최초 사용부터 구현까지

1. 설계 에이전트가 MCP로 프로젝트를 생성하고 원본 요구사항·참고 자료를 연결합니다.
2. UI는 문서가 없는 프로젝트를 빈 인덱스로 표시하고, 카탈로그에서 필요한 문서를 생성할 수 있음을 안내합니다.
3. 설계 에이전트가 카탈로그와 기존 문서를 조회하고 등록된 타입으로 설계를 작성합니다.
4. 사용자는 UI에서 실시간 변경을 확인하고 검토 의견·질문을 남깁니다.
5. 설계 에이전트가 피드백을 반영하고 사용자가 문서를 검토·승인합니다.
6. 별도의 구현 에이전트가 MCP로 프로젝트 인덱스를 조회하고 개발에 필요한 문서 본문을 가져갑니다.
7. 구현 에이전트는 승인 상태·근거·남은 가정과 질문을 확인한 뒤 외부 개발 환경에서 구현합니다.

## MCP 인계 계약

- 필수 기능 방향: 프로젝트 생성·조회, 카탈로그·문서 인덱스·본문 조회, 설계 문서 생성·수정, 입력과 검토 의견의 공유.
- 구현 에이전트가 검토 의견과 미결정 질문을 포함한 설계 맥락을 읽을 수 있어야 합니다.
- 문서 인덱스에는 ID·타입·제목 외 상태와 revision을 제공하는 방식을 사용합니다.
- 구현용 조회는 문서 ID와 revision을 지정하고 승인된 버전의 본문을 반환하는 계약을 사용합니다.
- 여러 문서를 읽는 동안 내용이 바뀌지 않도록 인계 목록에 `{ documentId, revision }` 쌍을 고정하는 방식을 사용합니다.
- UI는 체크한 순간의 승인 revision을 고정하며 선택한 버전을 별도 목록으로 표시합니다. 이후 SSE로 새 draft나 새 승인 버전을 받아도 자동 교체하지 않습니다. 현재 버전과 달라지면 안내하고, 사용자가 선택 해제하거나 새 승인 버전을 다시 선택하도록 합니다.
- 전체 카탈로그를 채울 필요는 없습니다. 개발 대상에 필요한 문서 집합을 선택합니다.
- 문서가 없거나 승인되지 않은 경우 조용히 최신 draft로 대체하지 않고 해당 상태를 반환합니다.
- 본문은 get_document, 승인 묶음은 get_handoff로 조회합니다. 초기 로컬 목록에는 페이지네이션을 두지 않으며 사용자별 권한은 제공하지 않습니다.
- 전체 프로젝트 자동 완료 판정은 하지 않습니다. 사용자가 필요한 승인 문서와 revision을 선택해 인계합니다.

## 검증 기준

- 새 프로젝트는 빈 문서 인덱스와 연결된 원본 입력을 조회할 수 있습니다.
- AI가 문서를 수정해도 원본 입력은 보존됩니다.
- 사용자는 본문 직접 편집 없이 질문·검토·승인을 수행하고 설계 에이전트는 피드백을 읽을 수 있습니다.
- draft 저장만으로 approved가 되지 않으며 승인 대상 revision을 구분합니다.
- 다른 구현 에이전트가 대화 기록 없이 MCP로 인덱스·본문·상태·입력 근거·가정·질문을 읽을 수 있습니다.
- 인계는 승인된 revision을 고정하며 이후 문서 수정에도 지정한 승인 버전 조회 결과를 유지합니다.
