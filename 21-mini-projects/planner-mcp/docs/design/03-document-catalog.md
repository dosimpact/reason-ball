# 문서 카탈로그와 프로젝트 문서

상태: 구현 기준. 실제 스키마·예시는 `get_catalog`, 추가 관계·Figma 수집은 [10](10-completion.md)을 따른다.

## 목적과 용어

Planner MCP는 비즈니스 요구사항과 Figma 정보를 frontend/BFF 개발 설계 문서로
가공하는 AI가 사용할 인터페이스를 제공합니다. 사용자는 프로젝트 스펙을 UI에서
시각적으로 관리하고 AI가 저장한 변경을 실시간으로 확인합니다.

이 문서의 카탈로그는 제품이 관리하는 설계 문서의 타입 목록입니다.
Planner MCP 자체의 개발 설계를 기록하는 저장소 `docs/design/` 목차와는 구분합니다.

| 개념 | 역할 | 관계 |
| --- | --- | --- |
| Project | 설계 문서의 관리 단위 | 여러 Document를 소유하며 문서가 없는 상태도 허용 |
| Document Catalog | 생성 가능한 문서 타입 목록 | 프로젝트 간 공통으로 참조하는 타입 정의 |
| Document Type | 문서 형식·검증·시각화의 기준 | 각 Document는 반드시 등록된 타입 하나를 선택 |
| Document | AI가 MCP로 생성·관리하는 실제 설계 문서 | 한 Project에 소속 |
| Project Document Index | 프로젝트에 실제 생성된 문서 목록 | 문서 식별 정보와 카탈로그 타입을 연결 |

전체 카탈로그는 “무엇을 만들 수 있는가”, 프로젝트 인덱스는 “무엇이 만들어져 있는가”를
나타냅니다. 프로젝트 인덱스를 카탈로그 조회라고 부르더라도 MCP 계약에서는 두 조회를 구분합니다.

## 초기 문서 카탈로그 (REQ-009, REQ-010)

타입 이름과 범위는 사용자 요구사항입니다. 아래 타입 ID와 시각화는 현재 구현에 채택했습니다.

| 문서 타입 | 타입 ID | 범위 | UI 시각화 |
| --- | --- | --- | --- |
| Upstream API Spec | `upstream-api-spec` | 기존·변경 상위 API 명세; BFF와 공통 내용 형식 | 공통 API 목록·상세 및 기존/변경 표시 |
| DB Entity 정의 문서 | `db-entity` | 엔티티와 관계를 Mermaid 형식으로 관리 | 확정: 엔티티 다이어그램 |
| BFF API Spec | `bff-api-spec` | 기존·변경 BFF API 명세; Upstream과 공통 내용 형식 | 공통 API 목록·상세 및 기존/변경 표시 |
| Weblogging Spec | `weblogging-spec` | 이벤트 발생 조건, 기록 대상, 각 필드 설명 | 이벤트별 조건과 기록 필드 설명 표 |
| Figma Requirements | `figma-requirements` | React widget 단위로 UI Surface, 입력 검증, UI Funnel 연결 | widget별 요구사항과 연결된 Figma 화면·노드 |
| Flow Spec Overview | `flow-spec-overview` | 비즈니스 핵심 개념·대상·동작과 주요 호출 경로 요약 | 공통 JSON 트리와 접기·펼치기. [Flow Spec 설계](04-flow-spec.md) 참조 |
| Flow Spec Detail | `flow-spec-detail` | 선택한 핵심 동작의 상세 단계와 호출·규칙 | Overview와 공통 JSON 트리·렌더러 사용 |

Figma Requirements의 세 항목은 현재 하나의 문서 타입이 포함하는 구성 요소입니다.
별도 문서 타입으로 분리한다는 요구사항은 없습니다.

DB Entity 문서는 애플리케이션이 관리하는 설계 산출물입니다. 이를 관리하기 위해
Planner MCP에 실제 DB를 도입하거나 DB 스키마를 실행하지는 않습니다.

## 생성 및 변경 규칙

- 등록된 문서 타입 선택은 생성의 필수 조건입니다. 타입이 없거나 알려지지 않은 타입이면 거부합니다.
- AI가 요청에 임의 타입 이름을 넣는 것으로 카탈로그를 확장할 수 없습니다.
- 타입별 형식 검증을 통과한 문서만 저장하도록 설계합니다.
- 프로젝트는 필요한 타입의 문서만 보유할 수 있습니다. 누락된 타입은 오류가 아닙니다.
- 동일 타입의 문서를 여러 개 허용하며 scope로 범위를 구분하고 UI 배지로 표시합니다. 생성 후 타입 변경은 거부합니다.
- scope와 타입별 작성 범위의 원본은 [타입별 작성 계약](07-document-type-contracts.md)입니다.
- 카탈로그 확장 시 타입 정의, 내용 검증, UI 시각화를 함께 추가하는 구조를 사용합니다.
- 카탈로그는 코드에 타입·스키마·예시·렌더러를 함께 등록합니다. 현재 schemaVersion은 1이며 다른 버전은 거부합니다.

## 저장 모델

- Project: 식별자, 이름, 설명, 원본 입력, 생성·수정 시각.
- Document: 문서 식별자, 프로젝트 식별자, 카탈로그 타입 ID, 제목, scope, 타입별 내용.
- Catalog Entry: 타입 ID, 표시 이름, 내용 형식·검증 규칙, 대응하는 UI 렌더러 정보.
- Project Document Index Entry: 문서 식별자, 제목, 타입 ID, scope. 상태·revision은 생명주기 계약을 따릅니다.
- DB Entity의 Mermaid 원문은 JSON 문서의 내용 필드에 문자열로 저장하는 방식을 사용합니다.
- Flow Spec은 JSON 트리를 내용으로 저장합니다. 텍스트 표현과 구분하며 [모델·탐색 설계](05-flow-spec-tree.md)를 따릅니다.
- 프로젝트 입력, 문서의 사실·가정·질문, 검토·승인 상태와 인계 메타데이터는 [설계 생명주기](06-design-lifecycle.md)를 따릅니다. 입력은 Project.sources, 설계 맥락은 공통 문서 메타데이터에 보존하며 별도 타입을 추가하지 않습니다.
- 인덱스는 저장된 문서에서 도출해 메모리에 캐시하며 별도 인덱스 파일은 두지 않습니다. [저장 계약](08-mcp-storage-sse.md)을 따릅니다.

## MCP와 UI 책임

- 설계 AI: 비즈니스 요구사항과 Figma 정보를 해석하고 설계 내용을 가공합니다.
- MCP: 프로젝트 생성·조회, 전체 타입 카탈로그 조회, 프로젝트 문서 인덱스·본문 조회 및 문서 생성·수정을 제공합니다.
- 구현 AI: 별도 에이전트로 MCP에서 필요한 설계를 읽고 외부 환경에서 개발합니다.
- 서버: 프로젝트 소속과 문서 타입·내용을 검증하고 JSON으로 저장하며 변경을 알립니다.
- UI: 프로젝트 인덱스와 시각화, 빈 화면, 검토·질문·승인을 제공하고 SSE 알림 후 최신 데이터를 조회합니다. Flow 노드 편집 외의 본문 작성은 MCP를 사용합니다.
- 새 문서가 생성되면 인덱스에 나타나고 열린 문서가 수정되면 해당 시각화가 갱신됩니다.
- Figma 직접 수집은 [10](10-completion.md)에 따라 제공합니다. 서버 내부 LLM 실행은 포함하지 않습니다.

## 검증 시나리오

- 카탈로그 조회에 초기 일곱 타입이 표시됩니다. Flow Spec Overview와 Detail은 별도 타입입니다.
- 미등록 타입 또는 타입 없는 생성 요청은 실패하며 문서·인덱스가 추가되지 않습니다.
- 문서가 없는 프로젝트는 빈 인덱스를 반환합니다.
- 일부 타입만 생성된 프로젝트는 해당 문서만 인덱스에 표시합니다.
- 같은 타입의 복수 문서와 각각의 scope가 인덱스·상세 UI에 표시됩니다.
- 프로젝트 A의 문서가 프로젝트 B의 인덱스에 섞이지 않습니다.
- DB Entity Mermaid 문서가 UI 엔티티 다이어그램으로 표시됩니다.
- Flow Spec의 단계 순서와 들여쓰기 계층이 저장·조회 및 UI 표시에서 유지됩니다.
- AI의 MCP 문서 생성·수정이 SSE를 통해 UI 인덱스와 열린 문서에 반영됩니다.
- 일곱 타입 모두 생산 브라우저 E2E에서 시각화를 검증합니다.
