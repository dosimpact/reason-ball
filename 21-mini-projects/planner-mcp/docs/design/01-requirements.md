# 요구사항

상태: 구현 기준 (사용자 요구사항은 확정, 실행 계약은 09·10 참조)

## 확정된 프로젝트 조건

- 패키지 이름: `planner-mcp`.
- 기존 pnpm workspace의 일부로 관리합니다.
- 구현 전에 요구사항과 아키텍처를 설계합니다.
- Todo List MCP를 기반으로 기능을 확장합니다.
- Next.js + TypeScript, JSON 파일 저장, SSE 변경 알림, FSD 디렉터리 구조, SLAP 및 순수함수 원칙을 적용합니다.
- 기반 원칙의 원본: [현재 설계 원칙](00-principles.md).

## 문제와 사용자

- 목적: 비즈니스 요구사항과 Figma 정보를 바탕으로 frontend 및 BFF 개발 설계 문서를 작성하고 프로젝트별로 관리합니다.
- 주요 사용자: 프로젝트 스펙을 관리하고 시각적으로 확인하는 사용자, MCP 인터페이스로 문서를 가공하는 AI.
- AI가 요구사항을 해석·가공하고 MCP를 통해 실제 설계 문서를 생성·관리하는 것이 핵심입니다.
- 사용자는 UI에서 프로젝트 문서와 시각화를 확인하고 변경 사항을 실시간으로 볼 수 있습니다.
- 설계 작성 에이전트와 별도로 구현 에이전트가 MCP로 설계 문서를 가져와 개발에 사용합니다.
- Streamable HTTP MCP 클라이언트를 사용합니다. Figma 파일·노드 읽기 연동은 [추가 기능 계약](10-completion.md)에 따라 제공하며 사용자 인증은 제외합니다.

## MVP 범위

- 프로젝트 생성과 빈 인덱스 화면, 원본 요구사항·참고 자료 연결, 카탈로그 기반 문서 관리를 포함합니다.
- 확정 사실·가정·미결정 질문을 구분하고 사용자의 검토·승인으로 문서 작성과 확정을 분리합니다.
- UI는 조회·시각화·검토·질문·승인과 Flow 노드 편집을 제공합니다. 다른 타입의 본문 작성은 MCP를 사용합니다.
- 별도 구현 에이전트가 MCP로 인덱스와 설계 본문을 조회하는 개발 인계를 포함합니다.
- 초기 카탈로그는 Upstream API Spec, DB Entity 정의 문서, BFF API Spec, Weblogging Spec, Figma Requirements, Flow Spec Overview, Flow Spec Detail의 일곱 타입입니다.
- Figma Requirements에는 UI Surface, Input Validation Requirement, UI Funnel Spec을 포함합니다.
- 같은 타입의 복수 문서를 허용하고 scope로 구분하며 UI에서 배지로 표시합니다.
- Upstream·BFF API Spec은 공통 문서 형식으로 기존·변경 스펙을 모두 관리합니다.
- Weblogging은 발생 조건과 기록 대상·필드 설명을 다루고, Figma Requirements는 React widget 단위로 관리합니다.
- DB Entity의 제약·인덱스·별도 필드 설명은 초기 필수 범위에서 제외합니다.
- 문서 타입별 UI 시각화와 SSE 기반 실시간 변경 반영을 포함합니다.
- DB Entity 문서는 Mermaid 형식으로 관리하고 UI에서 엔티티 다이어그램으로 표시합니다.
- Flow Spec은 코드 흐름의 중요한 단계를 들여쓰기로 표현해 논리 경로를 한눈에 보여줍니다.
- Flow Spec 전용 문법을 파싱해 UI에서 계층과 처리 단계를 접고 펼칠 수 있어야 합니다.
- 카탈로그는 추후 확장 가능해야 하며 프로젝트가 모든 타입의 문서를 가질 필요는 없습니다.
- 카탈로그에 없는 임의 타입 문서 생성은 허용하지 않습니다.
- Planner MCP 내부에서 frontend/BFF 코드를 생성·실행하지 않습니다. 실제 개발은 설계를 가져간 외부 구현 에이전트가 담당합니다.

## 대표 사용자 흐름

MCP 작성 작업은 조회 → 카탈로그·스키마 확인 → 본문 조회 → 수정안 검증 → 저장 순서로 안내합니다.
revision 충돌 감지, 재시도 중복 방지, 문서별 저장 결과, 오류·파일·SSE 계약은
[MCP·저장·SSE 설계](08-mcp-storage-sse.md)의 수락된 방향을 따릅니다.

1. 사용자가 설계 AI에 비즈니스 요구사항과 필요한 Figma 정보를 전달하고 AI가 프로젝트 생성 및 입력 연결을 수행합니다.
2. AI가 MCP로 대상 프로젝트, 문서 카탈로그, 현재 프로젝트 문서 인덱스를 조회합니다.
3. AI가 필요한 카탈로그 타입을 선택해 frontend/BFF 설계 내용을 작성하고 MCP로 문서를 생성·수정합니다.
4. 서버가 타입과 내용을 검증하고 프로젝트에 소속된 문서로 JSON 저장합니다.
5. UI가 SSE 변경 알림을 받아 프로젝트 인덱스와 문서 시각화를 갱신합니다.
6. 사용자가 UI로 검토·질문하고 설계 AI가 반영한 문서를 승인합니다.
7. 별도 구현 AI가 MCP로 인덱스와 필요한 설계 본문을 가져와 개발합니다.

카탈로그 및 인덱스의 세부 개념은 [문서 카탈로그 설계](03-document-catalog.md)를 참조합니다.
입력·검토·승인·인계의 원본은 [설계 생명주기](06-design-lifecycle.md)입니다.

## 후속 검토와 현재 결정

실행 기본값은 [09](09-implementation.md), 채택한 확장과 범위는 [10](10-completion.md)이 원본입니다. 아래 질문 중 구체화된 내용은 두 문서를 따르며 별도 미구현 요구사항으로 해석하지 않습니다.

- 프로젝트 수정·삭제와 문서 삭제·버전 보존의 범위는 무엇인가?
- scope 문자열 규칙·등록 방식과 같은 scope 내 문서 구분 정책은 무엇인가?
- 각 문서 타입의 필수 필드와 저장 스키마, 아직 정하지 않은 타입별 시각화 방식은 무엇인가?
- Figma는 링크, 추출 결과, 직접 연동 중 어떤 방식으로 입력받는가?
- MCP 도구 이름과 입출력 계약, 사용자 승인 권한 검증 방식은 무엇인가?
- 원본 입력은 프로젝트 부속 데이터와 카탈로그 문서 중 어느 형태로 보관하는가?
- 프로젝트 전체의 설계 완료와 구현에 필요한 승인 문서 집합은 어떻게 지정하는가?
- 데이터 보존, 사용자 구분, 접근 제어가 필요한가?
